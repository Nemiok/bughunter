# `@bughunter/node` — пресет для HTTP-API

Проверяет локальный HTTP-сервис так же доказательно, как веб-пресет проверяет страницу: каждая
находка воспроизводится в чистой сессии, каждый подтверждённый баг экспортируется в красный
Vitest-тест, вердикт которого получен независимым запуском.

Единица исследования — **эндпоинт** (`«МЕТОД /шаблон»`, например `GET /orders/:id`), действие — один
HTTP-запрос, симптом — статус 4xx/5xx, внутренности приложения в теле (стек, `ECONNREFUSED`) или
аномальный токен, оракул — `status`, `jsonPath` или `headerContains`.

## Установка

```bash
cd .qwen/bughunter && npm ci          # один lockfile на core и оба пресета
```

`.mcp.json` проекта должен указывать на точку входа node-пресета:

```json
{
  "mcpServers": {
    "bughunter": {
      "command": "node",
      "args": [".qwen/bughunter/presets/node/src/index.ts"]
    }
  }
}
```

Один проект = один пресет: при запуске сервер проверяет маркер `state/preset.json` и отвечает
`PRESET_CONFLICT`, если каталог состояния уже занят другим пресетом. Требуется Node.js ≥ 22.18.

Промпт-слой пресета лежит в его дереве и ставится вместе с ним: агенты —
[`agents/`](agents) (`bh-explorer`, `bh-reviewer`, `bh-test-writer`), карта инструментов —
[`skills/preset-card/SKILL.md`](skills/preset-card/SKILL.md). Общие правила берутся из core-скиллов
`bughunter`, `bughunter-oracles`, `bughunter-red-test`.

## Конфиг

`presets/node/state/config.json` создаётся при первом запуске (`CONFIG_CREATED`) и дальше
принадлежит оператору. Поля сверх общей схемы core:

| Поле | Зачем |
| --- | --- |
| `baseUrl` | адрес локального стенда |
| `allowedHosts` | запросы вне списка отклоняются как `FORBIDDEN_ORIGIN` до отправки |
| `profile` | имя профиля с инвентарём эндпоинтов (обязательно) |
| `scenarios` | объявленные сценарии обхода: `valid`, `empty`, `invalid`, `boundary` на эндпоинт, с ожиданием `expect.status` и `expect.jsonPath` |
| `reset` | рецепт возврата стенда в исходное состояние, например `{ "method": "POST", "path": "/__reset" }`; `null` — сброса нет |
| `requestTimeoutMs` | таймаут запроса, по умолчанию 10 000 |
| `detectors.anomalyTexts` | токены, которые считаются симптомом в теле ответа |
| `detectors.ignoreStatuses` | статусы, которые не считаются симптомом |

Общие поля (`limits`, `safety`, `targetMap`, `tests`, `baseBranch`) объявляет core. `safety.readOnly`
оставляет только GET/HEAD/OPTIONS, `safety.forbiddenActionText` ищется в строке «метод + путь + тело».

## Профиль и инвентарь

Инвентарь объявляется в `state/profiles/<имя>/index.ts` — автообхода роутеров и генерации из
OpenAPI в пресете нет:

```ts
export default {
  endpoints: [
    { method: 'GET', template: '/orders/:id', samplePath: '/orders/ord-1', description: 'Один заказ' },
  ],
  testDataDir: './test-data',
};
```

Цель прогона — строка `«МЕТОД /шаблон»`, поэтому `GET /orders` и `POST /orders` разные цели, а
`/orders/12` и `/orders/7f3ab4c9` относятся к `GET /orders/:id`. Принадлежность сценария цели
определяется по шаблонам профиля; сценарий, не подходящий ни к одному эндпоинту, отклоняется как
`SCENARIO_INVALID`.

## Области прогона

- `diff` — цели из `targetMap` по файлам, изменённым относительно `baseBranch`;
- `full` — весь инвентарь модельным исследованием (очередь «эндпоинт × персона»);
- `target <МЕТОД /шаблон>` — один эндпоинт модельным исследованием;
- `sweep` — детерминированный обход всего инвентаря без расхода модели;
- `sweep <МЕТОД /шаблон>` — обход одного эндпоинта;
- `resume <runId>` — продолжить незавершённые этапы.

## Инструменты

Пять инструментов пресета:

- `bh_open` — открыть сессию исследования эндпоинта (`runId`, `target`, `persona`, `leaseId`);
- `bh_state` — инвентарь, последние ответы (тела усечены до 2 КБ), новые симптомы, остаток шагов;
- `bh_act` — один HTTP-запрос (`method`, `path`, `body`, `headers`);
- `bh_sweep` — детерминированный обход с курсором и чекпоинтами;
- `bh_close` — закрыть сессию и сохранить дамп ответов `responses.jsonl`.

Одиннадцать инструментов core одинаковы у всех пресетов: `bh_start_run`, `bh_resume_run`,
`bh_explore_next`, `bh_finish_run`, `bh_report_candidate`, `bh_reproduce`, `bh_triage`,
`bh_promote_finding`, `bh_export_test`, `bh_detect_tests`, `bh_verify_red`.

Экспортируемый тест — Vitest без импортов bughunter: `fetch` к `baseUrl`, сброс стенда, запросы
журнала по порядку и одно утверждение на симптом. Каталог назначения — `tests.generated.dir`.

## Ограничения

- Оракул судит по **последнему ответу сессии**: кандидат без шагов не воспроизводится, у API
  нечего наблюдать без запроса.
- Сигнатура кандидата-оракула учитывает `pointer`, но не тело запроса: два разных запроса к одному
  эндпоинту с одинаковым ожиданием считаются одним багом.
- Разъезд схемы ответа (поле то `totalCents`, то `total`) не детектируется: нужен мини-оракул схемы.
- Неидемпотентность находится только последовательностью запросов, поэтому обход её не ловит.
- `reset` без рецепта даёт находку `reset-unsupported`: цели проверены в состоянии, которое оставили
  предыдущие запросы, и выдавать их за проверенные начисто нельзя.

## Приёмка

```bash
cd .qwen/bughunter/presets/node
BH_NODE_ACCEPTANCE=1 npm run acceptance     # обход → промоция → повтор → экспорт → red
```

Приёмка пишет измеренный базовый уровень в `fixtures/node-api-app/ACCEPTANCE.md`: сколько дефектов
найдено, сколько пропущено и почему, сколько красных тестов получено. Без флага её тесты
пропускаются, чтобы обычная линия оставалась быстрой.
