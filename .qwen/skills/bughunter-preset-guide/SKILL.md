**Пример копируй, core подключай.** Учебный пресет `presets/web` — это образец раскладки, а не библиотека для наследования: скопируй его и замени домен, а core подключай именем пакета `@bughunter/core` и реализуй его интерфейсы. Наследование от другого пресета запрещено так же, как правки core: иначе два пресета связаны чужим доменом. Контракт и состав интерфейсов описаны в скилле `bughunter-core-contract` — прочитай его первым.

## Шаг 1. Скопируй пример

```bash
cp -R presets/web presets/<name>          # src/, test/, tsconfig.json, package.json
rm -rf presets/<name>/state               # состояние примера не наследуется
```

Дальше правь только `presets/<name>`. `core/` не меняется ни на строку — это критерий приёмки, а не пожелание.

## Шаг 2. Пакет

- `package.json`: имя `@bughunter/<name>`, `"type": "module"`, `engines.node >= 22.18`, зависимость `"@bughunter/core": "*"`, скрипты `test` (`node --test --test-concurrency=1 test/*.bhtest.ts`), `typecheck`, `start` (`node src/index.ts`). Свои рантайм-зависимости добавляй сюда же: core их не тянет.
- Корневой `package.json` монорепо: добавь `"presets/<name>"` в `workspaces`, затем `npm install` — core придёт workspace-симлинком, один lockfile на всё дерево.
- `tsconfig.json` оставь как в примере: сборка не нужна, Node исполняет `.ts` снятием типов.
- `.mcp.json` проекта: команда `node .qwen/bughunter/presets/<name>/src/index.ts`, имя сервера — `bughunter` (его разрешают по имени в user settings, поэтому переименование стоит пользователю ручных действий).

## Шаг 3. Ответь на пять вопросов

Пять вопросов контракта — это порядок реализации. Каждый ответ ложится в интерфейсы:

- единица исследования → `TargetInventory` (`src/inventory.ts` в твоей раскладке);
- как увидеть и что сделать → `Session`, `SessionHandle`, `Snapshot`, словарь действий;
- что симптом → `Detectors`;
- какое нарушение проверяется → `Checks` (свой словарь видов `check`);
- как повторить и какой тест собрать → `Replay`, `TestGenerator`, `TestRunner`.

Затем девять хуков: `TestRunner`, `Personas`, `FindingKinds`, `SweepVisit`, `Reset`, `ExportTarget`, `Errors`, `ReportFormat`, `ProfileSchema`. Собери их в объект `Preset` (по образцу `presets/web/src/preset.ts`) и проверь `assertPreset`: недостающее поле даст `PRESET_INVALID: <поле>` при старте сервера, а не в середине прогона.

Пока интерфейс не реализован, держи в слоте заглушку, бросающую доменный код ошибки, — как `pending(hook)` в примере: сервер стартует, а непроверенная возможность не выдаёт себя за работающую (инвариант 7).

## Шаг 4. Инструменты и точка входа

`src/index.ts` — точка входа MCP-сервера. Одиннадцать имён core фиксированы и регистрируются одинаково у всех пресетов; инструменты взаимодействия — твой словарь (у web их восемь: `bh_open`, `bh_state`, `bh_act`, `bh_navigate`, `bh_probe`, `bh_crawl`, `bh_sweep`, `bh_close`). Схемы аргументов пиши `z.strictObject`: лишнее поле модели должно отклоняться сразу, а не игнорироваться.

`bh_open` и `bh_close` не изобретай: это тонкие обёртки над lease-фасадом core (`createLifecycle`), порядок «validate lease → open → record exploring → откат при неудаче» и «close → complete/release» существует в одном экземпляре, и именно им доказан resume-гейт. Доменные коды ошибок переводи на границе (`Errors.codes`), чтобы модель видела лексику своего пресета, а не нейтральные коды core.

## Шаг 5. Конфиг и профиль

Схема конфига — `commonConfigSchema.extend({ … })`: общие поля (`baseBranch`, `profile`, `targetMap`, `limits`, `safety`, `testDataPrefix`, `tests.unit.command`, `tests.generated.dir`) принадлежат core, свои (`baseUrl` у web, `allowedHosts` у node) объявляешь ты. Шаблон конфига создаётся при первом запуске (`CONFIG_CREATED`), несоответствие схеме отклоняется с именем поля (`CONFIG_INVALID: <файл>: <проблема>`).

Инвентарь приложения не дублируй в конфиг: ограничение области прогона живёт в `config.json` (он про установку), инвентарь — в профиле приложения (он про приложение). Профиль загружает `ProfileSchema`; new application = new profile, пресет при этом не правится.

## Шаг 6. Минимальное целевое приложение

Для приёмки не нужны фикстуры bughunter: возьми минимальное целевое приложение своего домена и засей в него баги перечислением в коде. Образец — CLI-утилита учёта заказов, четыре засеянных бага и одна чистая команда для контроля ложных срабатываний.

```js
// cli-app/src/cli.js — целевое приложение: учет заказов в JSON-файле.
// Реестр засеянных багов — в SEEDED.md; единственный источник правды — этот код.
import { existsSync, readFileSync, writeFileSync } from 'node:fs';

const db = process.env.DB_FILE ?? 'orders.json';
const read = () => (existsSync(db) ? JSON.parse(readFileSync(db, 'utf8')) : []);
const [command, ...args] = process.argv.slice(2);

if (command === 'add') {
  const [name, qty] = args;
  const rows = read();
  const total = Number(qty) * 100;      // C2: количество не проверяется, C4: нечисловое дает NaN
  rows.push({ name, qty: Number(qty), total });
  writeFileSync(db, JSON.stringify([...rows], null, 2));  // C3: повторный add пишет вторую строку
  console.log(`ok ${name} total=${total}`);
} else if (command === 'show') {
  const row = read().find((item) => item.name === args[0]);
  console.log(row.total);               // C1: неизвестное имя — необработанное исключение и стек наружу
} else if (command === 'list') {
  console.log(JSON.stringify(read()));  // контроль: команда всегда корректна
} else {
  console.error(`unknown command: ${command}`);
  process.exit(2);
}
```

| # | Баг | Класс | Как находится |
| --- | --- | --- | --- |
| C1 | `show` неизвестного имени падает со стеком и кодом 1 | сигнал | детектор stderr и кода выхода |
| C2 | `add -5` принимает отрицательное количество и дает total=-500 | инвариант | `check` на stdout |
| C3 | повторный `add` с теми же аргументами пишет вторую строку | кратность | `check` после двух вызовов |
| C4 | `add x abc` печатает `total=NaN` | аномальный токен | детектор stdout |
| — | `list` всегда корректен | контроль | ложных срабатываний быть не должно |
```
```

Засеянные баги держи в реестре с зеркалом в коде: приёмка считает покрытые и пропущенные, и пропуск обязан быть измеренным базовым уровнем в отчёте, а не умолчанием. Один баг оставь заведомо недостижимым для своего домена — так же, как web-пресет не находит разъезд схемы ответа API: это проверяет честность отчёта.

## Шаг 7. Тесты пресета

- `test/<name>-acceptance.bhtest.ts` — детерминированная приёмка без модели (по образцу `presets/web/test/bi-app-acceptance.bhtest.ts`): обход инвентаря, находки, промоция, воспроизведение, экспорт теста, вердикт `red`. Держи её под флагом, если она медленная.
- `test/portable.bhtest.ts` — stdio-рукопожатие в копии поставки: `initialize` → `tools/list`, состав инструментов и изоляция каталога состояния.
- `test/prompts.bhtest.ts` — контракт промптов: allowlist инструментов в агентах, словарь карты пресета, обязательные фразы.
- Свой тест направления импортов — запрет `from '.*presets/` и `@bughunter/<other>` внутри `core/` и внутри своего пресета.

Прогон: `npm test --workspaces --if-present` из корня монорепо. Зелёная линия примера (web) — 253 pass, 0 fail, 1 skipped; свои тесты добавляй к ней, не ослабляя чужие.

## Шаг 8. Приёмка

Приёмка проводится в одноразовой копии вне `.qwen/` (CLI отклоняет запись в чувствительные пути), с настроенным `.mcp.json` и без действий пользователя: сервер называется `bughunter` и уже разрешён по имени.

1. **Ноль правок core** — diff ветки пуст по `core/`, тесты направления импортов и запрета лексики зелёные.
2. **Детерминированный слой** — приёмка из шага 7 проходит без модели, за минуты.
3. **Модельный слой** — один прогон в копии: найдено не меньше 3 из 4 засеянных багов и **0** подтверждённых ложных срабатываний; пропуски опубликованы измеренным базовым уровнем.
4. **Red-доказательство** — на каждый подтверждённый баг есть тест с вердиктом `red`, полученным независимым запуском, а не со слов модели.
5. **Автоматическая линия** — весь набор монорепо зелёный, `typecheck` зелёный, web-пресет проходит route-репетицию.
6. **Гайдлайны проверены, а не декларированы** — отдельный headless-агент собирает игрушечный пресет для нового вида цели, читая только скиллы и примеры поставки. Провал — дефект гайдлайнов (конкретное место, где пришлось угадывать), а не дефект агента; до двух итераций, каждая со свежим агентом и свежей копией.

Артефакт приёмки — отчёт в `docs/superpowers/reports/` и сохранённый игрушечный пресет в `docs/concept/examples/` как второй учебный пример: в `presets/` он не попадает, потому что не поддерживается.
