**Пример копируй, core подключай.** Для нового домена основной учебный образец — `docs/concept/examples/cli-preset/preset`: скопируй его и замени домен, а core подключай именем пакета `@bughunter/core` и реализуй его интерфейсы. Для браузерного домена дополнительно ориентируйся на `presets/web`, для HTTP — на `presets/node`. Наследование от другого пресета запрещено так же, как правки core: иначе два пресета связаны чужим доменом. Контракт и состав интерфейсов описаны в скилле `bughunter-core-contract` — прочитай его первым.

## Шаг 1. Скопируй пример

Команда выполняется из корня репозитория Bughunter:

```bash
cp -R docs/concept/examples/cli-preset/preset .qwen/bughunter/presets/<name>
rm -rf .qwen/bughunter/presets/<name>/state
```

Дальше правь только `.qwen/bughunter/presets/<name>` и собственную фикстуру. В standalone-копии вместо этой раскладки работай внутри скопированного `cli-preset`: сервер — `preset/src/index.ts`, фикстура — `cli-app/`; plugin-автор использует `AUTHORING.md`, а не создаёт репозиторный `.mcp.json`. `core/` не меняется ни на строку — это критерий приёмки, а не пожелание.

## Шаг 2. Пакет

- `package.json`: имя `@bughunter/<name>`, `"type": "module"`, `engines.node >= 22.18`, зависимость `"@bughunter/core": "*"`, скрипты `test` (`node --test --test-concurrency=1 test/*.bhtest.ts`), `typecheck`, `start` (`node src/index.ts`). Свои рантайм-зависимости добавляй сюда же: core их не тянет.
- Корневой `.qwen/bughunter/package.json` монорепо: добавь `"presets/<name>"` в `workspaces`, затем выполни `npm install` из `.qwen/bughunter` — core придёт workspace-симлинком, один lockfile на всё дерево.
- `tsconfig.json` оставь как в примере: сборка не нужна, Node исполняет `.ts` снятием типов.
- `.mcp.json` в корне репозитория Bughunter: команда `node .qwen/bughunter/presets/<name>/src/index.ts`, имя сервера — `bughunter`. В standalone-копии путь указывает на `preset/src/index.ts` этой копии. Не переноси standalone-путь в репозиторий или репозиторный путь в plugin без пересчёта расположения точки входа.

## Шаг 3. Ответь на пять вопросов

Пять вопросов контракта — это порядок реализации. Каждый ответ ложится в интерфейсы:

- единица исследования → `TargetInventory` (`src/inventory.ts` в твоей раскладке);
- как увидеть и что сделать → `Session`, `SessionHandle`, `Snapshot`, словарь действий;
- что симптом → `Detectors`;
- какое нарушение проверяется → `Checks` (свой словарь видов `check`);
- как повторить и какой тест собрать → `Replay`, `TestGenerator`, `TestRunner`.

После ответов собери финальный чек-лист из девяти хуков: `TestRunner`, `Personas`, `FindingKinds`, `SweepVisit`, `Reset`, `ExportTarget`, `Errors`, `ReportFormat`, `ProfileSchema`. `TestRunner` уже назначен в пятом вопросе; остальные восемь ещё не назначены. Это не девять дополнительных интерфейсов поверх пяти вопросов. Собери все слоты в объект `Preset` по образцу `docs/concept/examples/cli-preset/preset/src/preset.ts` и проверь `assertPreset`: всего требуется 18 полей — 16 интерфейсов плюс `name` и `configSchema`. Недостающее поле даст `PRESET_INVALID: <поле>` при старте сервера, а не в середине прогона.

Пока интерфейс не реализован, держи в слоте заглушку, бросающую доменный код ошибки: сервер стартует, а непроверенная возможность не выдаёт себя за работающую (инвариант 7). Заглушка — приём разработки, а не поставляемое состояние: к приёмке (шаг 8) все слоты обязаны быть заполнены, потому что прогон с незаполненным хуком не пройдёт ни один критерий. В поставляемых пресетах заглушек нет: `pending(` и `PRESET_HOOK_NOT_WIRED` запрещены в `presets/*/src/preset.ts`, и это проверяет `core/test/contract-usage.bhtest.ts` — оставленная заглушка покраснит тест ядра, а не только твой собственный.

## Шаг 4. Инструменты и точка входа

`src/index.ts` — точка входа MCP-сервера. Одиннадцать имён core фиксированы и регистрируются одинаково у всех пресетов; инструменты взаимодействия — твой словарь (у web их восемь: `bh_open`, `bh_state`, `bh_act`, `bh_navigate`, `bh_probe`, `bh_crawl`, `bh_sweep`, `bh_close`). Схемы аргументов пиши `z.strictObject`: лишнее поле модели должно отклоняться сразу, а не игнорироваться.

`bh_open` и `bh_close` не изобретай: это тонкие обёртки над lease-фасадом core (`createLifecycle`), порядок «validate lease → open → record exploring → откат при неудаче» и «close → complete/release» существует в одном экземпляре, и именно им доказан resume-гейт. Доменные коды ошибок переводи на границе (`Errors.codes`), чтобы модель видела лексику своего пресета, а не нейтральные коды core.

## Шаг 5. Конфиг и профиль

Схема конфига — `commonConfigSchema.extend({ … })`: общие поля (`baseBranch`, `profile`, `targetMap`, `limits`, `safety`, `testDataPrefix`, `tests.unit.command`, `tests.generated.dir`) принадлежат core, свои (`baseUrl` у web, `allowedHosts` у node) объявляешь ты. Шаблон конфига создаётся при первом запуске (`CONFIG_CREATED`), несоответствие схеме отклоняется с именем поля (`CONFIG_INVALID: <файл>: <проблема>`).

Инвентарь приложения не дублируй в конфиг: ограничение области прогона живёт в `config.json` (он про установку), инвентарь — в профиле приложения (он про приложение). Профиль загружает `ProfileSchema`; new application = new profile, пресет при этом не правится.

**Направление оракула — самое важное решение приёмки.** `scenarios[].expect` в `config.json` — это **требуемое** поведение, а не зафиксированное. У засеянного бага `expect` обязан расходиться с фактическим выводом: сценарий `add tea -5` объявляет валидацию (ненулевой код и внятное сообщение), а не текущий `total=-500`. Если записать в `expect` фактический вывод, ревьюер законно отклонит находку как «соответствует объявленному контракту» — и приёмка покажет ноль найденных багов при формально зелёном прогоне. То же правило у `check` кандидата и у сгенерированного теста: они утверждают требуемое. Тест, зафиксировавший фактическое (`assert.equal(exitCode, 1)` на падении), всегда зелёный и баг не ловит.

`limits.candidatesPerRun` только валидируется схемой и нигде не энфорсится: не используй его как работающую защиту. `LIMIT_REACHED` для числа шагов сессии проверяет пресет при выполнении действия; отдельного core-хука нет.

`tests.unit.command` возвращается из `bh_detect_tests` и передаётся в `TestRunner.command` как `unitCommand`. Пресет сам решает, применима ли общая команда к однофайловому red-вердикту. CLI-шаблон показывает её при detect, но verify запускает собственный `node:test` TAP-wrapper, чтобы получить однозначный отчёт по одному файлу; не обещай, что configured command всегда исполняется.

## Шаг 6. Минимальное целевое приложение

Для приёмки не нужны фикстуры bughunter: возьми минимальное целевое приложение своего домена и засей в него баги перечислением в коде. Образец — CLI-утилита учёта заказов, четыре засеянных бага и одна чистая команда для контроля ложных срабатываний.

```js
// cli-app/src/cli.js — целевое приложение: учет заказов в JSON-файле.
// Реестр засеянных багов — в SEEDED.md; единственный источник правды — этот код.
import { existsSync, readFileSync, writeFileSync } from 'node:fs';

const db = process.env.DB_FILE ?? 'orders.json';
const read = () => (existsSync(db) ? JSON.parse(readFileSync(db, 'utf8')) : []);
const [command, ...args] = process.argv.slice(2);

if (command === 'add') {
  const [name, qty] = args;
  const rows = read();
  const total = Number(qty) * 100;      // C2: количество не проверяется, C4: нечисловое дает NaN
  rows.push({ name, qty: Number(qty), total });
  writeFileSync(db, JSON.stringify([...rows], null, 2));  // C3: повторный add пишет вторую строку
  console.log(`ok ${name} total=${total}`);
} else if (command === 'show') {
  const row = read().find((item) => item.name === args[0]);
  console.log(row.total);               // C1: неизвестное имя — необработанное исключение и стек наружу
} else if (command === 'list') {
  console.log(JSON.stringify(read()));  // контроль: команда всегда корректна
} else {
  console.error(`unknown command: ${command}`);
  process.exit(2);
}
```

```markdown
<!-- cli-app/SEEDED.md -->
| # | Баг | Класс | Как находится |
| --- | --- | --- | --- |
| C1 | `show` неизвестного имени падает со стеком и кодом 1 | сигнал | детектор stderr и кода выхода |
| C2 | `add -5` принимает отрицательное количество и дает total=-500 | инвариант | `check` на stdout |
| C3 | повторный `add` с теми же аргументами пишет вторую строку | кратность | `check` после двух вызовов |
| C4 | `add x abc` печатает `total=NaN` | аномальный токен | детектор stdout |
| — | `list` всегда корректен | контроль | ложных срабатываний быть не должно |
```
```

Засеянные баги держи в реестре с зеркалом в коде: приёмка считает покрытые и пропущенные, и пропуск обязан быть измеренным базовым уровнем в отчёте, а не умолчанием. Хотя бы один баг оставь недостижимым для детерминированного sweep при объявленных сценариях и reset, но не обязательно недостижимым для модели. Например, повторный `add` не виден sweep, если перед каждым сценарием база сбрасывается, а последовательность из двух `add` не объявлена; модель может построить эту последовательность сама. Пропуск sweep опубликуй с измеренным базовым уровнем — это проверяет честность отчёта.

## Шаг 7. Тесты пресета

- `test/acceptance.bhtest.ts` — детерминированная приёмка без модели: обход инвентаря, находки, промоция, воспроизведение, экспорт теста, вердикт `red`. Держи её под флагом, если она медленная.
- `test/preset.bhtest.ts` — поля `Preset`, словари и stdio-рукопожатие в копии поставки: `initialize` → `tools/list`, состав инструментов и изоляция каталога состояния.
- `test/prompts.bhtest.ts` — контракт промптов: allowlist инструментов в агентах, словарь карты пресета, обязательные фразы.
- `test/import-boundary.bhtest.ts` — запрет относительных импортов через `presets/` и пакетов `@bughunter/<other>` внутри своего пресета; `@bughunter/core` разрешён. Core отдельно проверяет собственный запрет импортов пресетов, поэтому standalone-шаблон не ищет внешний core.

Сгенерированный тест — **TypeScript**: не переименовывай его в `.js`, Node не снимает типы с `.js`, и файл не загрузится. И убедись, что созданный файл действительно запускается раннером пресета: падение загрузки (неверное расширение, синтаксис) — не красный тест, даже если раннер показал его как упавший. Читай сообщение падения: утверждение симптома, а не `SyntaxError`.

Имя файла задаёт `ExportTarget.fileName(bugId)`, а не core. В CLI-шаблоне это `${bugId}.test.ts`; при смене соглашения обнови generator/export tests и убедись, что раннер обнаруживает файл.

Прогон: `npm test --workspaces --if-present` из корня монорепо. Зелёная линия примера (web) — 0 fail при одном пропущенном тесте под флагом замера стоимости; точные счётчики намеренно не пишем, они устаревают в том же коммите. Свои тесты добавляй к этой линии, не ослабляя чужие.

## Шаг 8. Приёмка

Приёмка проводится в одноразовой копии вне `.qwen/` (CLI отклоняет запись в чувствительные пути), с настроенным `.mcp.json` и без действий пользователя: сервер называется `bughunter` и уже разрешён по имени.

1. **Ноль правок core** — diff ветки пуст по `core/`, тесты направления импортов и запрета лексики зелёные.
2. **Детерминированный слой** — приёмка из шага 7 проходит без модели, за минуты.
3. **Модельный слой** — один прогон в копии: найдено не меньше 3 из 4 засеянных багов и **0** подтверждённых ложных срабатываний; пропуски опубликованы измеренным базовым уровнем.
4. **Red-доказательство** — на каждый подтверждённый баг есть тест с вердиктом `red`, полученным независимым запуском, а не со слов модели.
5. **Автоматическая линия** — весь набор монорепо зелёный, `typecheck` зелёный, web-пресет проходит route-репетицию.
6. **Гайдлайны проверены, а не декларированы** — отдельный headless-агент собирает игрушечный пресет для нового вида цели, читая только скиллы и примеры поставки. Провал — дефект гайдлайнов (конкретное место, где пришлось угадывать), а не дефект агента; до двух итераций, каждая со свежим агентом и свежей копией.

Артефакт приёмки — отчёт в `docs/superpowers/reports/` и сохранённый игрушечный пресет в `docs/concept/examples/` как второй учебный пример: в `presets/` он не попадает, потому что не поддерживается.
