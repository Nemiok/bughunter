# Промпт: Bughunter для Kimi Code CLI — каркас и MVP

Ты — senior TypeScript-инженер. Реализуй open source инструмент **Bughunter** для агентного CLI **Kimi Code CLI** (команда `kimi`, модели Kimi из подписки Kimi Code). Это набор файлов внутри папки `.kimi-code/` целевого проекта: без npm-публикации, без плагинов и без сборки. Инструмент исследует веб-приложение на дев-стенде как реальный пользователь, находит баги, детерминированно их воспроизводит и пишет на них тесты.

Работай поэтапно (см. «Порядок работы»). После каждого этапа запускай тесты и давай короткий отчёт: что сделано, что проверено, какие решения приняты.

## Контекст и ограничения

- Работает **локально** на машине разработчика. CI нет. Сервер Bughunter не делает внешних сетевых вызовов, кроме дев-стенда; к облаку Kimi обращается только сам CLI.
- Запуск: `/bughunter` внутри уже запущенной сессии `kimi`. Модель предоставляет CLI. Поле `model` у агентов **не использовать**, `[secondary_model]` не настраивать: субагенты наследуют модель сессии.
- Длинные цепочки вызовов ненадёжны для любой модели, а детерминизм нужен для воспроизведения. Поэтому вся логика, которую можно сделать кодом (обход, детекторы, лимиты, безопасность, воспроизведение, генерация e2e, запуск тестов), живёт в MCP-сервере. LLM только принимает решения: что нажать, чем заполнить, баг ли это, как написать unit-тест.
- Браузер — только Chrome. Используй установленный Chrome через `channel: 'chrome'`, без скачивания браузеров. Если Chrome не найден, понятная ошибка с подсказкой.
- Тестовые фреймворки целевых проектов разные (Jest в приложении, Vitest в ui-kit). Привязки к одному фреймворку нет.
- Стиль кода: современный TypeScript (strict, ESM), минимум зависимостей, без лишних абстракций. Комментарии на русском, только к неочевидным местам. Не усложняй: выбирай самое простое рабочее решение.

## Состав и размещение

Всё лежит в `.kimi-code/` целевого репозитория. Всё, что относится к Bughunter, имеет префикс `bughunter` или `bh-`, чтобы папку можно было скопировать в другой репозиторий (например, из приложения в ui-kit) одной командой `cp -r`.

```

  agents/bh-reviewer.md
  agents/bh-test-writer.md
  skills/bughunter-oracles/SKILL.md
  skills/bughunter-red-test/SKILL.md
  bughunter/
    .gitignore                     # server/node_modules/, state/runs/, state/auth/
    server/                        # код; при обновлении заменяется целиком
      package.json                 # "type": "module", зависимости сервера
      package-lock.json
      tsconfig.json                # только для проверки типов, Node его не читает
      src/
        index.ts                   # MCP stdio-сервер, регистрация инструментов
        auth.ts                    # npm run auth: ручной вход и сохранение storageState

        detectors/                 # консоль, pageerror, сеть, аномалии текста, error boundary
        reproduce.ts               # повтор журнала и минимизация шагов
        export/playwright.ts       # журнал действий → Playwright-тест
        tests/detect.ts            # определение фреймворка и команды запуска
        tests/verify-red.ts        # запуск теста и вердикт red/green/broken
      test/                        # тесты сервера (node:test), файлы *.bhtest.ts
      fixtures/buggy-app/          # демо-приложение с засеянными багами
      README.md
    state/                         # данные; при обновлении не трогать
      config.json
      known-bugs.json
      suppressions.json
      auth/storage-state.json      # в .gitignore

```

### Запуск без сборки

- Сервер — TypeScript, выполняемый Node ≥ 22.18 напрямую (встроенный type stripping). Только стираемый синтаксис: без `enum`, `namespace`, parameter properties; импорты с расширением `.ts`. В `tsconfig.json`: `erasableSyntaxOnly`, `verbatimModuleSyntax`, `allowImportingTsExtensions`, `noEmit`. `npm run typecheck` вызывает `tsc` только для проверки.
- Зависимости: `@modelcontextprotocol/sdk`, `playwright-core` (не `playwright`: без скачивания браузеров в postinstall), `zod`; в devDependencies — `typescript`, `@types/node`. Ставятся один раз: `cd .kimi-code/bughunter/server && npm ci` из корпоративного npm-зеркала. `node_modules` игнорируется собственным `.kimi-code/bughunter/.gitignore`, так что корневой `.gitignore` проекта трогать не нужно.
- При старте сервер проверяет версию Node и наличие `node_modules`. При проблеме — одна понятная ошибка с командой исправления.
- Путь к `state/` вычисляется от расположения сервера (`import.meta.dirname` + `../state`), поэтому от рабочей директории не зависит. Корень проекта для `git diff` и запуска тестов — ближайший вверх каталог с `.git`.

Подключение в `.kimi-code/mcp.json` (stdio-сервер, `kimi` запускается из корня репозитория):

```json
{
  "mcpServers": {
    "bughunter": {
      "command": "node",
      "args": [".kimi-code/bughunter/server/src/index.ts"],
      "startupTimeoutMs": 30000,
      "toolTimeoutMs": 600000
    }
  }
}
```

Рабочая директория stdio-сервера в документации не описана: на этапе 0 проверить, относительно чего разрешается путь в `args`. Если не от корня проекта — добавить поле `cwd`. `toolTimeoutMs` нужен для долгих `bh_reproduce` и `bh_verify_red`.

Проектные MCP-серверы Kimi Code включает только после подтверждения доверия к папке. Об этом — первым пунктом в README.

Чтобы каждый шаг исследователя не требовал подтверждения, в README описать правило в `config.toml` пользователя:

```toml
[[permission.rules]]
decision = "allow"
pattern = "mcp__bughunter__*"
```

Это допустимо, потому что ограничения безопасности зашиты в код сервера, а не в промпт.

### Изоляция от инструментов проекта

Код Bughunter не должен попадать в сборку, линт и тесты целевого проекта:
- тесты сервера имеют суффикс `.bhtest.ts`, который не совпадает со стандартными шаблонами Jest и Vitest;
- в README — проверка, что `tsconfig`, ESLint, Jest и Vitest проекта не включают `.kimi-code/`, и что добавить в исключения, если включают.

## Данные

Состояние лежит в `.kimi-code/bughunter/state/`. Конфиг и общая память (`known-bugs.json`, `suppressions.json`) коммитятся и расходятся по команде через git. `runs/` и `auth/` в `.gitignore`.

```
state/runs/<runId>/
  run.json           # scope, маршруты, статусы этапов (для resume)
  candidates/<id>.json
  journals/<sessionId>.json
  artifacts/<id>/    # trace.zip, screenshot.png, video.webm
  e2e/               # экспортированные тесты, если в проекте нет Playwright
  report.md
```

`config.json` (валидировать через zod, давать понятные ошибки):

```json
{
  "baseUrl": "https://dev-stand.example.local",
  "allowedOrigins": ["https://dev-stand.example.local"],
  "routes": ["/", "/orders", "/orders/new", "/profile"],
  "routeMap": { "src/pages/orders/**": ["/orders", "/orders/new"] },
  "baseBranch": "main",
  "limits": { "stepsPerSession": 60, "candidatesPerRun": 20 },
  "safety": { "forbiddenActionText": ["удалить", "delete", "оплатить"], "readOnly": false },
  "testDataPrefix": "bh_",
  "detectors": {
    "ignoreConsole": [],
    "ignoreRequests": [],
    "anomalyTexts": ["undefined", "NaN", "[object Object]", "Invalid Date"],
    "errorBoundarySelector": "[data-error-boundary]"
  },
  "tests": { "unit": { "command": null }, "e2e": { "dir": "e2e/bughunter" } }
```

Если `config.json` нет, первый вызов `bh_start_run` создаёт шаблон и возвращает ошибку `CONFIG_CREATED` с путём к файлу.

`npm run auth` в папке сервера открывает Chrome в обычном режиме на `baseUrl`, ждёт ручного входа и сохраняет `state/auth/storage-state.json`.

## MCP-инструменты

Все входы описаны zod-схемами, выход — компактный JSON. Описания инструментов короткие и на русском: модель выбирает инструмент по описанию. Ответы минимальны, никаких полных DOM и логов.

| Инструмент | Вход | Выход и поведение |
|---|---|---|
| `bh_start_run` | `scope: 'diff' \| 'full' \| 'route'`, `route?` | `{ runId, routes }`. Для `diff` берёт `git diff --name-only <baseBranch>...HEAD` и сопоставляет файлы с маршрутами по `routeMap`; если совпадений нет — все `routes` |
| `bh_resume_run` | `runId` | Состояние этапов и необработанные кандидаты |
| `bh_open` | `runId`, `route`, `persona` | `{ sessionId }`. Новый контекст с `storageState`, трассировка и видео включены |
| `bh_state` | `sessionId` | `{ url, title, elements: [{ id, role, name, type, value?, disabled? }], signals: [...новые с прошлого вызова], stepsLeft }`. Только видимые интерактивные элементы, имена обрезаны до 80 символов |
| `bh_act` | `sessionId`, `elementId`, `action: 'click' \| 'dblclick' \| 'fill' \| 'select' \| 'press' \| 'check' \| 'hover'`, `value?` | `{ ok, error?, navigated, signals }`. Пишет шаг в журнал с семантическим локатором |
| `bh_navigate` | `sessionId`, `path` | Переход только внутри `allowedOrigins` |
| `bh_probe` | `sessionId`, `kind: 'reload' \| 'back' \| 'mobile_viewport'` | Выполняет пробу, возвращает новые сигналы. Пробы тоже пишутся в журнал |
| `bh_report_candidate` | `sessionId`, `title`, `expected`, `actual`, `signalIds[]`, `check?` | `{ candidateId, duplicateOf? }`. Сохраняет кандидата и срез журнала. Сразу сверяет сигнатуру с `known-bugs.json` и `suppressions.json` в `state/`. `check` нужен для багов без сигнала (нарушение инварианта): `{ kind: 'visibleText' \| 'notVisibleText' \| 'elementCount', target, expected? }`. Сигнатура в этом случае строится по `check` и маршруту |
| `bh_close` | `sessionId` | Закрывает контекст, сохраняет артефакты |
| `bh_reproduce` | `runId`, `candidateId`, `attempts = 3` | `{ reproduced: 'k/n', steps, signature, artifacts }`. Повтор журнала в чистом контексте; баг считается воспроизведённым, если появился тот же сигнал или нарушен `check`. Затем минимизация: удаление шагов по одному, пока сигнал воспроизводится, не более 20 повторов. Общее время инструмента — не более 5 минут |
| `bh_triage` | `runId`, `candidateId`, `verdict: 'confirmed' \| 'rejected' \| 'duplicate'`, `reason`, `suppress?` | Обновляет `known-bugs.json` или `suppressions.json` |
| `bh_export_e2e` | `runId`, `bugId` | `{ file, placedInProject }`. Генерирует Playwright-тест из минимальных шагов. Если в проекте есть `@playwright/test`, кладёт в `tests.e2e.dir`, иначе — в `runs/<runId>/e2e/`. Ассерт — на конкретный симптом: отсутствие `pageerror` с этой сигнатурой, статус ответа, отсутствие аномального текста или ожидаемое значение из `check` |
| `bh_detect_tests` | `path` | `{ framework: 'jest' \| 'vitest' \| null, command, examples: [пути до 3 соседних тестов] }`. По ближайшему `package.json` и конфигам; `tests.unit.command` из конфига имеет приоритет |
| `bh_verify_red` | `testFile` | `{ status: 'red' \| 'green' \| 'broken', message }`. Запуск одного файла с JSON-репортером. `red` — падение на ассерте; `broken` — синтаксис, импорт, таймаут, ошибка вне ассерта. `message` обрезан до 1 500 символов. Таймаут запуска — 2 минуты |
| `bh_finish_run` | `runId` | `{ report }`. Пишет `report.md`: подтверждённые баги, шаги, артефакты, созданные тесты, отклонённое |

### Детекторы (детерминированные, без LLM)

- `console.error`, необработанные исключения (`pageerror`), `requestfailed`, ответы со статусом ≥ 500 и 4xx, кроме `ignoreRequests`.
- Текстовые аномалии из `anomalyTexts` в видимом тексте страницы. Совпадение только по целым словам или токенам.
- Появление `errorBoundarySelector`.
- Сигнатура сигнала: хэш от типа, нормализованного сообщения (без чисел, id, url-параметров), шаблона маршрута и верхнего кадра стека. По сигнатуре работают дедупликация и подавление.
- Для MVP стеки используются как есть, без source maps.

### Локаторы в журнале

Приоритет: `data-testid` → `getByRole(role, { name })` → `getByText` → CSS. Сохраняется вместе с индексом при неоднозначности. Повтор и экспорт используют те же локаторы.

### Безопасность (только в коде, не в промптах)

- Любой переход вне `allowedOrigins` блокируется.
- `bh_act` отказывает, если текст или имя элемента совпадает с `forbiddenActionText`, а в режиме `readOnly` — также для отправки форм.
- По исчерпании `stepsPerSession` сервер возвращает ошибку `LIMIT_REACHED`.
- `fill` без явного значения подставляет `testDataPrefix` + случайный суффикс.

## Точка входа, агенты, скиллы

Промпты короткие, императивные, на русском, с явными критериями остановки. Длинные знания — в скиллах, а не в системных промптах. Отдельных пользовательских команд в Kimi Code нет: точка входа — скилл `bughunter`, который вызывается как `/bughunter` (сокращение от `/skill:bughunter`).

Имена инструментов: встроенные — `Read`, `Write`, `Edit`, `Grep`, `Glob`, `Bash`, `Agent`, `Skill` (регистр важен), MCP — `mcp__bughunter__<tool>`, в `tools` допустимы маски вида `mcp__bughunter__*`.

**`skills/bughunter/SKILL.md`** — frontmatter: `name: bughunter`, `description`, `disableModelInvocation: true` (запуск только вручную), тело использует `$ARGUMENTS`. Аргументы: `diff` (по умолчанию), `full`, `route <path>`, `resume <runId>`. Основной агент держит свой контекст тонким и не открывает браузер сам. Порядок:
1. `bh_start_run` или `bh_resume_run`.
2. Для каждого маршрута последовательно делегирует через `Agent` субагенту `bh-explorer`, передавая `runId`, маршрут и персону (не в фоне, по одному). Персоны MVP: «новичок» (основные сценарии), «нетерпеливый» (двойные клики, быстрые переходы, reload и back), «граничный ввод» (пустые, длинные, юникод, отрицательные числа, спецсимволы).
3. Для каждого кандидата вызывает `bh_reproduce`. Невоспроизведённые помечает и не передаёт дальше.
4. Воспроизведённых передаёт `bh-reviewer`, подтверждённые — `bh-test-writer`.
5. `bh_finish_run` и краткая сводка пользователю: найдено, подтверждено, созданные файлы. Ничего не коммитит.

Все агенты — Markdown с frontmatter `name`, `description`, `tools`, `subagents: []` (дальнейшее делегирование запрещено). Тело самодостаточное, без `${base_prompt}`, и заканчивается требованием: «последнее сообщение — полный самостоятельный результат для вызывающего агента», потому что пользовательские субагенты работают без встроенной рамки передачи результата.

**`agents/bh-explorer.md`** — `tools`: `mcp__bughunter__bh_open`, `bh_state`, `bh_act`, `bh_navigate`, `bh_probe`, `bh_report_candidate`, `bh_close` (полными именами), `Skill`. Цикл: `bh_state` → одно действие → оценка сигналов. Кандидат регистрируется только при наличии детерминированного сигнала или нарушения инварианта, которое выражается через `check` (например, после двойного клика `elementCount` строк заказа должен вырасти на 1). Стоп по `LIMIT_REACHED`, при исчерпании идей или после 5 кандидатов. Возвращает список `candidateId` с однострочным описанием, без логов.

**`agents/bh-reviewer.md`** — `tools`: `Read`, `Grep`, `Glob`, `mcp__bughunter__bh_triage`, `Skill`. Читает только `.kimi-code/bughunter/state/runs/` (указать в теле). Проверяет, что сигнал воспроизводится, относится к приложению (а не к стенду, расширению браузера или сторонним скриптам) и не дублирует известный баг. Сомнительное — `rejected` с причиной.

**`agents/bh-test-writer.md`** — `tools`: `Read`, `Grep`, `Glob`, `Edit`, `Write`, `mcp__bughunter__bh_detect_tests`, `mcp__bughunter__bh_export_e2e`, `mcp__bughunter__bh_verify_red`, `Skill`. `Bash` не давать: тесты запускает `bh_verify_red`. Для каждого бага:
1. Вызвать `bh_export_e2e`. Если тест лёг в проект, проверить его через `bh_verify_red`.
2. Найти причину по стеку и маршруту. Если место найдено уверенно — написать unit-тест рядом с существующими тестами модуля, в их стиле (по `examples` из `bh_detect_tests`), и добиться `red` не более чем за 3 итерации.
3. Если причина не найдена — unit-тест не писать, указать причину в итоге.
4. Код приложения не менять никогда.

**`skills/bughunter-oracles/SKILL.md`** — что считать багом, иерархия надёжности сигналов, частые ложные срабатывания (ошибки сторонних скриптов, ожидаемые 401/404, сетевые проблемы стенда), формат «ожидалось / получено». В `whenToUse` — «при исследовании страницы и разборе кандидатов в баги».

**`skills/bughunter-red-test/SKILL.md`** — правила «красного» теста: один тест на один симптом, конкретный ассерт (не `toBeTruthy` и не «не упало»), без фиксированных `sleep`, без зависимости от порядка данных и времени, изоляция и очистка состояния. Различия Jest и Vitest (`jest.fn` / `vi.fn`, моки модулей, таймеры). В `whenToUse` — «при написании теста на найденный баг».

## Демо-приложение для проверки

`server/fixtures/buggy-app` — минимальное Vite + React + TS приложение (свой `package.json`, ставится отдельно только для разработки Bughunter) с Vitest, `@playwright/test` для экспортированных e2e и парой обычных unit-тестов (как образец стиля). Засеять 5 багов, у каждого понятная причина в коде:

1. Кнопка «Сохранить» на `/profile` кидает необработанное исключение при пустом имени.
2. Отправка формы `/orders/new` при количестве `0` даёт ответ 500 от мок-API.
3. Двойной клик по «Создать заказ» создаёт два заказа.
4. Итоговая сумма на `/orders` показывает `NaN` при пустом списке.
5. После reload на `/orders?page=2` фильтр сбрасывается и показывается ошибка в консоли.

Мок-API — минимальный Vite middleware, без отдельного сервера. Плюс одна страница без багов для проверки отсутствия ложных срабатываний.

## Порядок работы

0. **Сверка с Kimi Code CLI.** Проверь на установленной версии `kimi` (документация: https://www.kimi.com/code/docs/en/kimi-code-cli/): рабочую директорию stdio-сервера из `.kimi-code/mcp.json`; что `/bughunter` разрешается в `/skill:bughunter` и не занято системной командой; что пользовательские агенты из `.kimi-code/agents/` видны основному агенту и вызываются через `Agent`; что субагент с `tools`, содержащим `Skill`, может загрузить проектный скилл. Расхождения вынеси в один список в README.
1. **Сервер, ядро.** Проверки окружения при старте, конфиг, хранилище run, `bh_start_run`, `bh_open`, `bh_state`, `bh_act`, `bh_navigate`, `bh_probe`, `bh_report_candidate`, `bh_close`, все детекторы, безопасность, демо-приложение. Интеграционные тесты: скриптовый (без LLM) проход по демо-приложению находит сигналы багов 1, 2, 4, 5 и не даёт сигналов на чистой странице.
   **Проверка гипотезы (стоп-точка).** Минимальный `bh-explorer` и ручной прогон в `kimi` по каждому маршруту демо-приложения на модели сессии. Если кандидаты есть меньше чем по 3 багам из 5, остановись и доложи: какие шаги делала модель, где застряла. Дальше не иди — сначала дорабатываются `bh_state`, промпт исследователя и персоны.
2. **Воспроизведение и e2e.** `bh_reproduce` с минимизацией, `bh_triage`, `bh_export_e2e`. Тест: для каждого засеянного бага экспортированный Playwright-тест падает на демо-приложении и проходит после исправления бага в копии.
3. **Unit-тесты.** `bh_detect_tests`, `bh_verify_red` для Jest и Vitest. Тест на фикстурах (мини-проекты с Jest и с Vitest внутри `server/fixtures/`): красный, зелёный и сломанный тест получают верные статусы в обоих фреймворках.
4. **Точка входа, агенты, скиллы.** `skills/bughunter/SKILL.md`, три агента, два скилла, фрагмент `mcp.json`. Проверка: копия демо-приложения выносится в отдельный каталог с `git init` (Kimi Code ищет корень проекта по `.git`), в неё копируется `.kimi-code/`, затем ручной прогон `/bughunter full` на демо-приложении. Ожидание: не менее 4 из 5 багов подтверждены, ноль подтверждённых ложных срабатываний, для каждого подтверждённого бага есть красный e2e-тест.
5. **README.** Установка в проект: скопировать файлы, `npm ci`, дописать `mcp.json`, доверить папку при первом запуске `kimi`, добавить правило разрешений, `npm run auth`, заполнить `config.json`. Перенос в другой репозиторий и обновление без потери `state/`. Сценарии запуска, ограничения MVP, список мест для сверки с Kimi Code CLI.

## Не делать в MVP

npm-публикация и плагины Kimi Code, AgentSwarm и фоновые субагенты, `[secondary_model]`, CI, Cypress, другие браузеры, создание MR и задач в GitLab или Jira, source maps, визуальные и перф-проверки, параллельные исследователи, внедрение сетевых сбоев, поле `model` у агентов, переопределение встроенных агентов (`override`).

## Критерии готовности

- Все интеграционные тесты этапов 1–3 проходят командой `npm test` в `.kimi-code/bughunter/server` без LLM.
- Сервер запускается командой `node src/index.ts` без шага сборки; `npm run typecheck` проходит.
- Прогон `/bughunter full` на демо-приложении соответствует ожиданию этапа 4.
- Повторный `/bughunter resume <runId>` после прерванной сессии продолжает с необработанных кандидатов.
- Никакие действия вне `allowedOrigins` и запрещённые действия невозможны независимо от того, что запросила модель.
