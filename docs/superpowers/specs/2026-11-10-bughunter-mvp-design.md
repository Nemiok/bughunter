# Bughunter MVP — дизайн

## Контекст

Bughunter — локальный open source инструмент для Kimi Code CLI, который исследует веб-приложение на дев-стенде, детерминированно воспроизводит найденные ошибки и создаёт красные e2e и, при уверенном нахождении причины, unit-тесты. Продукт распространяется как переносимый набор файлов `.kimi-code/`, без npm-публикации, плагинов и шага сборки.

Нормативные детали интерфейсов и состава файлов находятся в `Bughunter для Kimi Code CLI  промпт на каркас и MVP.md`. Этот документ фиксирует утверждённую архитектуру, потоки данных, обработку ошибок и порядок проверки. Реализуются все этапы 0–5 с сохранением ручных стоп-точек.

## Принятые решения

- Реализация ведётся строго по этапам исходной спецификации. Сквозной срез и подход «сначала агенты» отклонены: они либо увеличивают переделки, либо откладывают безопасность и воспроизводимость.
- Вся детерминированная логика находится в MCP-сервере. LLM выбирает действия, оценивает кандидатов и пишет unit-тесты, но не управляет лимитами, безопасностью, воспроизведением или классификацией результата теста.
- Используются Node ≥22.18, строгий TypeScript ESM со стираемым синтаксисом, `@modelcontextprotocol/sdk`, `playwright-core` и `zod`. Браузер — только установленный Chrome через `channel: 'chrome'`.
- Код располагается в `.kimi-code/` текущего каталога `bughunter`. Исходный репозиторий и его уже существующие изменения не затрагиваются.
- Промпты и агенты пишутся на русском, без поля `model`, без `[secondary_model]`, фоновых исследователей и дальнейшего делегирования.

## Архитектура

### MCP-сервер

`server/src/index.ts` проверяет окружение и регистрирует инструменты с zod-схемами, короткими русскими описаниями и компактными JSON-ответами. При старте выдаётся одна понятная ошибка для неподдерживаемой версии Node или отсутствующих зависимостей, включая команду исправления.

Модули имеют одну ответственность:

- `config.ts` — загрузка и валидация конфигурации, создание шаблона при первом `bh_start_run` и ошибка `CONFIG_CREATED`.
- `run-store.ts` — запуски, кандидаты, журналы, артефакты, статусы этапов и отчёты. JSON-файлы записываются атомарно через временный файл и rename.
- `browser/session.ts` — жизненный цикл Chrome-контекста, действия, пробы, журнал, сигналы, трассировка и видео.
- `browser/elements.ts` — видимые интерактивные элементы, стабильные идентификаторы в пределах снимка и семантические локаторы.
- `detectors/` — нормализация сигналов, сигнатуры, фильтры и дедупликация.
- `reproduce.ts` — чистые повторы, определение того же симптома и минимизация журнала.
- `export/playwright.ts` — генерация e2e из минимального журнала с одним ассертом на конкретный симптом.
- `tests/detect.ts` и `tests/verify-red.ts` — определение Jest/Vitest, запуск одного файла и классификация результата.

Путь к `state/` вычисляется от расположения сервера. Корень целевого проекта — ближайший вверх каталог с `.git`; для тестов и изолированных копий допускается явный внутренний параметр корня, не меняющий MCP-контракт.

### Агентный слой

Скилл `bughunter` — ручная точка входа `/bughunter`. Основной агент только управляет запуском, последовательно вызывает `bh-explorer` для каждого маршрута и персоны, затем воспроизведение, ревью, написание тестов и отчёт. Браузерные MCP-инструменты основному агенту не нужны.

`bh-explorer` выполняет цикл «снимок → одно действие → оценка сигналов». `bh-reviewer` читает только данные запусков и принимает решение о кандидате. `bh-test-writer` создаёт тесты, но никогда не меняет код приложения и не получает `Bash`. Все агенты возвращают полный самостоятельный результат вызывающему агенту.

### Демо и изоляция

`fixtures/buggy-app` — Vite + React + TypeScript с пятью засеянными ошибками, чистой страницей, Vitest и Playwright. Мок-API реализуется Vite middleware. Отдельные мини-проекты Jest и Vitest проверяют классификатор тестов.

Файлы серверных тестов имеют суффикс `.bhtest.ts`. Зависимости, запуски и авторизационное состояние игнорируются собственным `.kimi-code/bughunter/.gitignore`; корневой `.gitignore` целевого проекта не изменяется.

## Данные и основной поток

1. `bh_start_run` валидирует конфигурацию, выбирает маршруты для `diff`, `full` или `route`, создаёт `run.json` и возвращает `runId`.
2. `bh_open` создаёт изолированный контекст с сохранённым `storageState`, трассировкой и видео. `bh_state` возвращает URL, заголовок, только видимые интерактивные элементы, новые сигналы и остаток шагов.
3. `bh_act`, `bh_navigate` и `bh_probe` выполняют одно безопасное действие и добавляют в журнал семантический локатор либо пробу. Приоритет локаторов: `data-testid`, роль с именем, текст, CSS; неоднозначность сохраняется индексом.
4. Детекторы независимо от модели регистрируют `console.error`, `pageerror`, сетевые ошибки и статусы, текстовые аномалии по целым токенам и error boundary. Сигнатура строится из типа, нормализованного сообщения, шаблона маршрута и верхнего кадра стека.
5. `bh_report_candidate` сохраняет кандидата и срез журнала, сравнивает сигнатуру с известными багами и подавлениями. Для нарушения инварианта без сигнала обязателен детерминированный `check`.
6. `bh_reproduce` повторяет журнал в чистом контексте до трёх раз. Симптом подтверждён при той же сигнатуре сигнала или нарушении `check`. Затем шаги удаляются по одному, если симптом сохраняется; не более 20 повторов и пяти минут на весь вызов.
7. `bh_triage` обновляет состояние кандидата и общую память. `bh_export_e2e` использует минимальные шаги и конкретный ассерт симптома. Файл попадает в проект только при наличии `@playwright/test`, иначе остаётся в `state/runs/<runId>/e2e/`.
8. `bh_detect_tests` помогает написать unit-тест в стиле соседних файлов. `bh_verify_red` запускает один файл и отличает проваленный ассерт (`red`) от успеха (`green`) и ошибки запуска (`broken`).
9. `bh_finish_run` атомарно обновляет статус и пишет `report.md`. `bh_resume_run` возвращает состояние этапов и необработанных кандидатов, чтобы продолжить без повторной обработки завершённых.

## Безопасность и ошибки

- Любая навигация, включая клиентские переходы и новые страницы, ограничивается `allowedOrigins`. Внешний переход блокируется кодом, а не промптом.
- Действия с запрещённым текстом или именем отклоняются. В `readOnly` дополнительно блокируются отправки форм. Лимит шагов возвращает `LIMIT_REACHED`.
- `fill` без значения использует `testDataPrefix` и случайный суффикс.
- Долгие операции имеют дедлайны; браузеры, контексты, трассировка и дочерние процессы освобождаются в `finally` и при ошибках.
- Ошибки конфигурации содержат путь и конкретное поле. Отсутствие Chrome сопровождается подсказкой установить Chrome, а не скачивать браузер автоматически.
- Сетевые сбои стенда и ожидаемые ответы не объявляются подтверждёнными багами без ревью. Подавление и дедупликация опираются на сохранённые сигнатуры.
- `bh_verify_red` ограничен двумя минутами, `message` — 1500 символами. Таймаут и ошибка вне ассерта классифицируются как `broken`.

## Проверка

### Этап 0 — совместимость CLI

На установленной версии `kimi` и по официальной документации проверяются рабочая директория stdio MCP, разрешение `/bughunter` в `/skill:bughunter`, видимость пользовательских агентов и доступность проектного скилла субагенту. Все фактические расхождения собираются одним списком в README. Если MCP требует перезапуска или ручного доверия, это не маскируется автоматическим тестом.

### Этап 1 — ядро и гипотеза

Интеграционный проход без LLM обнаруживает сигналы ошибок 1, 2, 4 и 5 и не создаёт сигналов на чистой странице. Отдельно проверяются внешняя навигация, запрещённые действия, `readOnly`, лимиты и невалидная конфигурация.

Минимальный исследователь вручную запускается в `kimi` по каждому маршруту. Если кандидаты покрывают менее трёх из пяти багов, реализация останавливается; отчёт перечисляет действия модели и места застревания.

### Этап 2 — воспроизведение и e2e

Для каждого засеянного бага проверяются воспроизведение, минимизация и экспорт. Тест красный на исходном демо и зелёный на отдельной исправленной копии. Исходное демо остаётся сломанным.

### Этап 3 — unit-фреймворки

На Jest- и Vitest-фикстурах красный, зелёный и сломанный тесты получают верные статусы. Явно проверяются синтаксическая ошибка, ошибка импорта, сбой вне ассерта и таймаут.

### Этапы 4–5 — переносимость и документация

Демо копируется в отдельный каталог с `git init`, туда копируется `.kimi-code/`, затем вручную выполняется `/bughunter full`. Критерий: не менее четырёх подтверждённых багов, ноль подтверждённых ложных срабатываний и красный e2e на каждый подтверждённый баг. Повторный `/bughunter resume <runId>` продолжает необработанных кандидатов.

README описывает доверие к папке первым пунктом, установку через `npm ci`, слияние `mcp.json`, правило разрешений, `npm run auth`, конфигурацию, перенос, обновление без потери `state/`, изоляцию от инструментов проекта, ограничения MVP и расхождения CLI.

## Критерии готовности

- `npm test` в `.kimi-code/bughunter/server` проходит все автоматические проверки этапов 1–3 без LLM.
- `npm run typecheck` проходит; `node src/index.ts` запускает сервер без сборки.
- Ручные стоп-точки и критерии полного прогона либо выполнены, либо явно указаны как требующие действия пользователя; непроверенное не выдаётся за готовое.
- Невозможно обойти ограничения origins, запрещённых действий и лимитов через входы MCP.
- Ничего не коммитится и не публикуется автоматически.
