# Bughunter для BI-платформ — дизайн

Дата: 2026-11-12. Статус: **утверждён автором 2026-11-12** (включая добавление `@playwright/test` в репозиторий Навигатора). Предыдущий документ: `2026-11-10-bughunter-mvp-design.md` (MVP, остаётся в силе для ядра).

Документ прошёл проверку «свежим исполнителем» (builder check): 8 вопросов, где пришлось бы угадывать, закрыты в разделах 6–8. Ответы автора зафиксированы в разделе 6, решения исполнителя — в разделе 7.

## 1. Контекст и зачем

Bughunter сегодня — переносимый пакет для Qwen Code CLI: MCP-сервер с детерминированной логикой (обход, детекторы, лимиты, воспроизведение, триаж, экспорт, отчёт) плюс слой промптов (entry skill и три custom agent). MVP доказан на демо-фикстуре: три модельных прогона с нулём батчинга в оркестрации, красные e2e и unit-тесты на подтверждённые баги, детерминированные guard'ы на уровне сервера.

Но MVP настроен на небольшой DOM-SPA: несколько маршрутов, стабильные `data-testid`, классы багов, видимые через `console.error`, `pageerror`, HTTP ≥ 400, аномальные токены текста и error boundary.

Целевой продукт — **Навигатор BI**, собственное приложение автора: React, `react-konva` (canvas), `three.js` (WebGL), смешанный рендеринг (canvas + SVG + DOM), сотни экранов, короткие, но многочисленные сценарии, часть из них комплексные. Данные приходят с бэкенда, который **недоступен для изменений**; в проекте есть **MSW** (mock-service-worker), поэтому данные детерминированы в браузере. Docker отсутствует, приложение поднимается на локальном хосте корпоративного устройства. Playwright/e2e в репозитории Навигатора нет. shadow DOM не используется, iframe — исключение.

Доминирующий класс багов BI — **неверные данные**. Ни один текущий детектор его не наблюдает: расхождение между тем, что вернул API, и тем, что отрисовано, не порождает ни console-ошибки, ни HTTP-статуса, ни аномального токена.

Дальнейшая цель автора — эталонный инструмент поиска багов в веб-приложениях вообще, поэтому специфика Навигатора не должна протекать в ядро.

## 2. Цели, не-цели, анти-цели

### Цели

- **G1. Баги данных детерминированно.** Находить расхождения «ответ API ↔ проекция в UI» кодом, без заранее заданного человеком эталона: перехваченный ответ и есть эталон.
- **G2. Сотни экранов с управляемой стоимостью.** Обнаружение и шаблонизация маршрутов, приоритизация и дешёвый детерминированный «сверочный обход» экрана без участия модели.
- **G3. canvas и WebGL без пиксельных сравнений.** Читать отрисованную модель (граф Konva, граф сцены three.js), а не угадывать по скриншоту.
- **G4. Детерминированное воспроизведение и red-доказательство** на MSW-моках: seed-датасет и возврат стенда в известное состояние перед каждым повтором.
- **G5. Расширяемость.** Новое приложение = новый профиль; ядро не правится.
- **G6. Точность важнее полноты.** Отчёт читает человек; ложные срабатывания подавляются одним действием и не ослепляют инструмент глобально.

### Не-цели (этого дизайна)

- CI-режим, кластер, параллельные исследователи — фаза 3 и далее.
- Доступ к бэкенду, Docker, нагрузочное тестирование.
- Визуальная регрессия и пиксельный diff как оракул бага.
- Жизненный цикл SSO/токенов: авторизация мокируется MSW, существующий `auth.ts` достаточен.
- Обход iframe и shadow DOM в фазе 1 (iframe — исключение, shadow DOM отсутствует); точка расширения сохраняется.
- Ежедневный полный обход сотен экранов персонами: `full` — редкий длительный прогон, не основной режим (решение автора, раздел 6).

### Анти-цели (что делает результат провалом, даже если код работает)

- Шумный отчёт: легальные трансформации (округление, локаль, часовой пояс, агрегация) неотличимы от багов → разработчик перестаёт читать отчёт.
- Хрупкие доказательства: `red`-тест, который падает по инфраструктурной причине или не падает из-за гонки (такой дефект в MVP уже был найден и исправлен — гонка ассерта с ответом сети).
- BI-специфика в ядре: `src/**` знает про Konva, three.js, MSW или Навигатор.
- Недетерминированное воспроизведение: кандидат подтверждён, но повтор на другом состоянии стенда даёт другой результат.
- Обход защит координатными действиями: `isForbidden`/`readOnly` проверяют текст только для `click|dblclick|press` (`session.ts:497,505`), поэтому координатное действие, не разрешённое в семантическую цель, обязано отклоняться, а не выполняться.

## 3. Ограничения

- Node ≥ 22.18, TypeScript со стираемым синтаксисом, запуск без сборки; MCP stdio; браузер — только установленный Chrome через `channel: 'chrome'`.
- Локальный запуск на корпоративном устройстве: вероятны прокси и корпоративные сертификаты → нужны настраиваемые аргументы запуска Chrome (сейчас их нет).
- Бэкенд недоступен; единственный управляемый источник данных — MSW в браузере.
- Playwright отсутствует в целевом репозитории → без его добавления `bh_export_e2e` вернёт `placedInProject: false`, тест останется в `state/runs/…/e2e/` и `bh_verify_red` не сможет доказать `red` (риск R5, требует подтверждения владельца репозитория).
- Стоимость модельного времени: исследование строго последовательное (lease + `EXPLORER_BUSY`), поэтому экономия достигается областью прогона и детерминированной сверкой, а не параллелизмом.
- Существующие бюджеты: `limits.stepsPerSession` (в демо 60), `reproduce.ts`: ≤ 20 повторов и 5 минут на вызов, ≤ 3 попытки. Бюджеты становятся переопределяемыми на область прогона; механизм переопределения должен жить вне строгой zod-схемы `config.json` либо расширять её явно (схема сегодня `strictObject`, неизвестные поля отклоняются).

## 4. Рассмотренные варианты

**A. Эволюционный: профиль поверх текущего ядра.** Ядро сохраняется; добавляется слой профиля (экстракторы, оракулы, контракт полей, рецепт сброса, расширения действий), контекстные слушатели сети с телами ответов, новые действия (drag&drop, scroll, координатные click/hover, upload), кроулер маршрутов с шаблонизацией, ранжирование и лимит снимка.
*Даёт:* минимальный архитектурный риск, всё доказанное продолжает работать. *Стоит:* единица работы остаётся «маршрут × персона»; сотни экранов = сотни последовательных сессий.

**B. Сценарный: единица работы — пользовательский поток.** Очередь, журнал и lease перестраиваются под сценарии («датасет → график → фильтр → публикация») с контрольными точками и переносом состояния; оракулы считаются на контрольных точках.
*Даёт:* комплексные баги BI живут в потоках; один сценарий покрывает много экранов. *Стоит:* переделка `run-store`/очереди/журнала и нужен источник сценариев — высокий риск и стоимость входа.

**C. Инверсия: сначала оракулы, потом исследование.** Сравнение «ответ API ↔ проекция в UI» выполняется кодом на каждом достижимом экране; модель только доводит до экрана и разбирает находки.
*Даёт:* максимальная точность, минимальная стоимость находки, хорошо ложится на «экранов сотни». *Стоит:* находит только расхождения ответа и проекции; логика визардов, drag&drop и гонки всё равно требуют модели.

**Выбрано: A как скелет + C внутри него как основной BI-оракул с фазы 1 + задел под B** (решение автора). Обоснование: локальный исследовательский режим на сотнях экранов требует почти нулевой стоимости одного экрана — её даёт только детерминированная сверка (C); глубину взаимодействия закрывает A; B в любом случае зависит от слоя экстракторов и контрактов, поэтому без A/C не строится, а переписывать очередь под сценарии до появления профиля — риск без выигрыша.

Отклонено отдельно: **пиксельный diff / визуальная регрессия как оракул бага** — ломает принцип детерминированности (скриншот остаётся артефактом-доказательством, но не источником вердикта).

## 5. Архитектура

### 5.1 Слои

**Ядро (generic, `server/src/`)** не знает ни о BI, ни о Навигаторе: браузерная сессия и безопасность, журнал шагов, сигналы и сигнатуры, очередь задач и lease, воспроизведение и минимизация, триаж и память, экспорт и вердикты `red/green/broken`, отчёт, хранение состояния. Ограничение фиксируется тестом: в `src/**` нет упоминаний `konva`, `three`, `msw`, `navigator-bi`.

**Профиль приложения** — TS-модуль, типизированный контрактом ядра (`src/profile/types.ts`):

| Часть профиля | Что это | Где исполняется |
| --- | --- | --- |
| `extractors` | Именованные страничные функции, возвращающие структурированную проекцию виджета: таблица → заголовки и строки; Konva → граф/атрибуты узлов; three.js → состав сцены; DOM-виджет → тексты и атрибуты | В странице; обязаны возвращать сериализуемый JSON с лимитом размера (усечение помечается флагом) |
| `oracles` | Правила сравнения «ответ API ↔ проекция»: сопоставление URL-паттерна с виджетом и полями, допуски, характер расхождения (значение/формат/порядок/полнота) | В Node |
| `contract` (необязательно) | Декларативное описание полей: формат, единицы, округление, часовой пояс, допустимые агрегации; какие поля виджет проецирует | В Node |
| `reset` | Рецепт возврата стенда в известное состояние (см. 5.2.7) | В Node + страничная инициализация |
| `interactions` | Расширения набора действий, специфичные для приложения (например, как перетащить поле на полку) | В Node, реализация через действия ядра |
| `navigation` | Правила шаблонизации маршрутов: какие сегменты считать идентификаторами (`/dashboard/:id`) | В Node |
| `testData` | Каталог файлов для `upload` и сценарные датасеты | ФС профиля |

Профиль выбирается полем `profile` в `config.json`; на один `stateDir` — один активный профиль. Загрузка — на прогон, а не на процесс сервера, чтобы смена профиля не требовала перезапуска MCP.

### 5.2 Поток данных и новые возможности ядра

1. **Области прогона.** К `diff | full | route | resume` добавляются `screen <template>` (один экран) и `sweep` (детерминированный сверочный обход инвентаря **без участия модели**). **Основные режимы локальной работы — `diff`, `screen`, `sweep`** (решение автора). `full` остаётся редким длительным прогоном и потому обязан поддерживать чекпоинты: прерванный обход продолжается с курсора, а не начинается заново.
2. **Обнаружение маршрутов.** Новый инструмент `bh_crawl`: обход ссылок и клиентских переходов с шаблонизацией по правилам профиля; результат — инвентарь `state/screens.json` (шаблон маршрута, способы попадания, известные виджеты, дата последней проверки, курсор обхода). Инкрементальный: повторный обход добавляет новое, не перетирает старое. `sweep` и `full` работают по инвентарю; `routes` остаётся ограничителем области.
3. **Сетевой слой.** Слушатели поднимаются с `page` на `BrowserContext` (сейчас `signals.ts:82-110` слушает `page`), добавляется чтение тел ответов с ограничением размера. **Причина:** MSW отвечает из service worker, page-уровень может не видеть такие ответы вовсе. Порядок действий согласован с автором: **сначала спайк фазы 0** (видит ли Playwright SW-ответы и читаются ли тела); **если не видит — хук в MSW-слое** (`worker.events.on('response:mock')` → `window.__bhResponses`) как гарантированный запасной источник эталона. В фикстуре `bi-app` хук присутствует сразу, чтобы обе ветки были проверены, а не заявлены. Учёт того, что в `session.ts:444` уже стоит `context.route('**/*')` для блокировки внешних origin: новый перехват не должен ломать существующую политику, а `serviceWorkers: 'block'` неприменим, поскольку убивает MSW.
4. **Хранение тел ответов.** В журнале шага — нормализованный JSON с лимитом размера и хэшем содержимого; полное тело — отдельный артефакт `runs/<runId>/responses/<hash>.json`. В кандидата попадают только значения из расхождения (их требует отчёт), а не тела. Причина: журнал перезаписывается атомарно на каждый шаг (`session.ts:577`) и целиком копируется в `Candidate.steps` (`session.ts:315`), инлайновые тела раздули бы и то и другое на порядки.
5. **Сверка (вариант C).** После каждого действия/навигации ядро: определяет видимые виджеты экрана → для каждого вызывает экстрактор профиля → сравнивает с привязанным к нему ответом API по оракулу и контракту → расхождение регистрирует как находку. Привязка «URL-паттерн → виджет → поля» объявляется в `oracles` профиля, а не угадывается ядром. **Момент сверки — только после детерминированного ожидания именно привязанного ответа** (не `domcontentloaded` + макротаск, как в `settle()` `session.ts:543`): это прямой перенос урока гонки, из-за которой экспортированный спек давал `green` вместо `red`.
6. **Находки сверки — отдельная сущность.** `finding` не является `Candidate`: у неё нет журнала шагов и персоны, а существующий триаж требует `reproduction.status === 'reproduced'` (`run-store.ts:441`), и `reproduce` открывает сессию по `journal.route` с `journal.persona` (`reproduce.ts:180`). Для `finding` вводится свой режим повтора: `reset → navigate → extract → compare` (а не step-replay), со своим статусом и своим порогом подтверждений. `finding` становится `Candidate` только когда требуется interaction-сценарий или экспорт теста.
7. **Новые действия.** К `click | dblclick | fill | select | press | check | hover` (`types.ts:94`) добавляются `drag` (from → to), `scroll` (контейнер, направление, величина), `clickAt`/`hoverAt` (координаты; для Konva — разрешение через `stage.getIntersection({x,y})`), `upload` (файл из `testData` профиля). `Step` расширяется структурно (`from`/`to`/`at`/`file`), а не перегрузкой `value`. Координатные действия **обязаны** разрешиться в семантическую цель до проверок `isForbidden`/`isReadOnlySubmission`; если цель не разрешается — действие отклоняется. Минимизация (`reproduce.ts:114`) по-прежнему удаляет шаги целиком, но для координатных шагов добавляется проверка, что удаление не меняет разрешённую цель. Экспорт узнаёт новые формы шагов наравне с существующими четырьмя паттернами локаторов (`playwright.ts:37`).
8. **Воспроизведение и сброс.** Перед каждым повтором выполняется `reset` профиля. Базовый механизм (решение исполнителя по согласованию «самым точным и простым образом»): **флаг сценария в storage + перезагрузка** — он не попадает в URL, а значит не искажает `currentRoute()`, сигнатуры (`signals.ts:30`), `routeName()`/`routeStages` (`run-store.ts:278`) и экспортируемый спек. Уточнение для случаев, когда перезагрузка недопустима, — **служебный эндпоинт сброса моков** (точный сброс без навигации). Вариант «сценарий в query-параметре» отклонён именно из-за загрязнения маршрута и сигнатур. Наличие `reset` в профиле обязательно для сценариев, претендующих на детерминированное воспроизведение; если сброса нет, кандидат получает **флаг** `nonDeterministic` (не новый литерал `reproduction.status` — от него зависят `requiresWork()` `run-store.ts:371`, гейт триажа и гейт экспорта `playwright.ts:333`), воспроизведение переходит на сравнение «до/после», а экспорт помечает тест как нестрого детерминированный в отчёте и в имени.
9. **Снимок состояния.** Сегодня `elements.ts:142` возвращает все видимые интерактивные элементы без лимита, а `compactState` (`index.ts:130`) лишь убирает поле `locator`. Добавляются: ранжирование (в области просмотра → по роли → по размеру/позиции), лимит N с явной пагинацией (курсор в `bh_state`) и блок «структура экрана» — виджеты с типом, именем экстрактора и кратким содержимым (число строк, диапазоны, подписи осей), чтобы модель видела смысл экрана, а не сотни кнопок.
10. **Подавления становятся областными.** Сегодня `suppressions.json` хранит глобальные сигнатуры: один отказ на легальном округлении ослепил бы инструмент ко всему классу расхождений. Новая модель — `scope: { routeTemplate?, widget?, field?, kind }` + сигнатура; `bh_triage(rejected)` пишет областное подавление; отчёт содержит готовое действие «подавить это расхождение в этом виджете». Подавление применяется на эмиссии находки, но **учитывается в precision-метриках** как «подавлено», иначе метрика теряет смысл. Для `dataMismatch` вводится отдельный расчёт сигнатуры: стандартная `normalizeMessage` заменяет все числа на `<number>`, из-за чего путь поля `rows[3].total` схлопнулся бы и разные поля дали бы одну сигнатуру. Существующие глобальные записи мигрируют в областные с пустым `scope`.
11. **Отчёт.** Группировка экран → виджет → поле; разделение классов находок (баг данных / сигнальный баг / нарушение инварианта); precision-метрики прогона (заявлено, подтверждено, отклонено, подавлено); для каждого расхождения — значение из ответа и значение в UI, а не только факт несовпадения.
12. **Экспорт.** Для `dataMismatch` генерируется спек, который сам перехватывает привязанный ответ (`page.waitForResponse`) и сравнивает его с проекцией через экстрактор профиля, а не только сверяет sha256-сигнатуру (сигнатурный спек остаётся для сигнальных багов). Сохраняются принципы уже исправленного экспортёра: детерминированное ожидание завершения сети перед ассертом, наблюдение транзиентных состояний, один ассерт на симптом, единая с рантаймом политика маршрутов (граница — origin).

### 5.3 Изменения в промптах

- **`bh-explorer`**: работает со «структурой экрана», а не с плоским списком элементов; знает новые действия; явное правило — сверка ответа и проекции выполняется ядром автоматически, задача исследователя дойти до экрана, прожить сценарий и проверить инварианты поведения (включая кратность и идемпотентность эффекта — правило уже добавлено в оракулы), а не выискивать расхождения глазами.
- **`bh-reviewer`**: критерии для `dataMismatch` — отличить легальную трансформацию (контракт, формат, локаль, зона, агрегация) от бага; работа с областными подавлениями; запрет подтверждать расхождение без значения из ответа и значения в UI.
- **`bh-test-writer`**: экспорт data-теста (спек, читающий ответ и сравнивающий с проекцией), переиспользование хелперов целевого проекта, требование `red` не более чем за 3 итерации (сохраняется).
- **`bughunter-oracles`**: новый класс — согласованность данных; обновлённый порядок доверия: проверенный инвариант через `check` → расхождение ответа и проекции при наличии контракта → необработанное исключение/error boundary → ошибочный ответ API/console с трассировкой в код приложения → аномальный текст.
- **entry skill**: области `screen` и `sweep`, приоритизация по `diff`, правило не запускать модель там, где достаточно `sweep`.
- **Новый агент для `sweep` не нужен**: обход детерминированный и выполняется ядром; модель подключается только к находкам, требующим взаимодействия.

### 5.4 Фикстура `bi-app` (acceptance-эталон)

Стек намеренно совпадает с Навигатором: React + Vite + TypeScript + **MSW** + **react-konva** + **three.js**. Без совпадения стека приёмка проверит не те пути (в частности, introspection Konva и headless-WebGL).

**Экраны:** список дашбордов с пагинацией; дашборд с четырьмя виджетами — таблица (DOM), линейный график (SVG), столбчатый график (Konva canvas), 3D-сцена (three.js); редактор отчёта — визард из трёх шагов с drag&drop поля на полку; экран настроек с формой; «чистый» экран без ошибок (контроль ложных срабатываний).

**MSW:** версионируемые seed-датасеты; сценарии — нормальный, задержка сети, ошибка 500, пустые данные, большие данные (виртуализированная таблица); переключение сценария флагом в storage и перезагрузкой, плюс служебный эндпоинт сброса; хук `response:mock` → `window.__bhResponses` присутствует сразу как запасной источник эталона.

**Засеянные баги данных (5–7):** итог не равен сумме строк; округление не в ту сторону; сдвиг часового пояса; фильтр применён к одному виджету и не применён к другому; пагинация отдаёт дубль строки; формат числа в тултипе не соответствует локали; доля считается от неверной базы.

**Засеянные легальные трансформации (3–4) как приманка для ложных срабатываний:** «1.2K» вместо 1234; локальный формат «1 234,57»; дата в локальной зоне; итог, округлённый до копеек.

**Засеянные баги не про данные (2–3):** необработанное исключение; гонка при быстрой смене фильтра; двойная отправка формы.

**Тестовые крючки:** `window.__bhProfile` (идентификаторы виджетов и точки доступа к экстракторам), доступ к Konva stage и three.js scene, стабильные `data-testid`.

**Критерий приёмки:** доля найденных засеянных багов данных ≥ X и доля ложных срабатываний ≤ Y при нуле неподтверждённых ложных; X и Y фиксируются после первого калибровочного прогона, а не выдумываются заранее. Дополнительно: каждый подтверждённый баг имеет `red`-тест, доказанный `bh_verify_red`, и все `red` становятся `green` на исправленной копии фикстуры.

### 5.5 Фазы

**Фаза 0 — спайки (1–2 дня), до всякого кода.** (a) Видит ли Playwright ответы, обслуженные SW (MSW), на уровне `BrowserContext`, и читаются ли их тела — при отрицательном результате основным источником эталона становится MSW-хук (согласовано с автором). (b) Читается ли граф Konva из страницы — `Konva.stages`, контейнер `.konvajs-content` + React fiber, или нужен app-крючок. (c) Рендерится ли WebGL в headless Chrome на корпоративном устройстве и какие launch args обязательны. (d) Как надёжно сбрасывать сценарий MSW между повторами (storage-флаг + reload против служебного эндпоинта). Результат — письменные ответы; при провале (a) или (c) архитектура оракулов меняется до начала разработки.

**Фаза 1 — «запуск на BI» (ядро + профиль).** Контекстные слушатели сети с телами ответов и хранилищем тел; слой профиля и его контракт в ядре; новые действия (`drag`, `scroll`, координатные `clickAt`/`hoverAt`, `upload`) с разрешением в семантическую цель до guard'ов; ранжирование, лимит и пагинация снимка плюс «структура экрана»; настраиваемые аргументы запуска Chrome (прокси, сертификаты, `--use-gl=swiftshader`); `bh_crawl` + `screens.json` + шаблонизация; области `screen` и `sweep` с чекпоинтами. Критерий: на `bi-app` инструмент доходит до каждого экрана, видит ответы и проекции, выполняет drag&drop и координатные действия, снимок не превышает лимит, прерванный `sweep` продолжается с курсора.

**Фаза 2 — «ценность».** Оракул согласованности данных и находки `dataMismatch` с отдельной сигнатурой; режим повтора `reset → navigate → extract → compare`; областные подавления и отказ в одно действие; отчёт с группировкой и precision-метриками; экспорт data-теста и добавление Playwright в целевой репозиторий; полная фикстура `bi-app` с засеянными багами и легальными трансформациями; калибровка X/Y. Критерий: приёмка по 5.4 пройдена на `bi-app`.

**Фаза 3 — «масштаб» (после проверки на Навигаторе).** Задел под сценарии (вариант B): очередь и журнал принимают единицу работы «сценарий» с контрольными точками и переносом состояния; приоритизация по риску изменений и истории находок; при необходимости — параллелизм с настоящей изоляцией; CI-режим. Критерий: сценарный прогон не требует правок ядра, только профиля и очереди.

## 6. Решения, принятые автором

- Целевая платформа — Навигатор BI (собственный продукт), затем обобщение на произвольные веб-приложения.
- Режим работы — локально на машине разработчика, цель — **поиск неизвестных багов**; CI-режим не первичен.
- Архитектура — **A + C с заделом под B** (раздел 4).
- Легальные трансформации отличаем от багов **и контрактом, и подавлениями, старт через подавления**.
- Пиксельный diff как оракул — не делаем.
- Источник истины для оракула данных — перехваченный ответ API; работает и на моках MSW, и на живом бэкенде.
- **Эталон при SW/MSW:** сначала спайк фазы 0; если Playwright не видит ответы — хук в MSW-слое как запасной путь. Правки чужого бэкенда не предполагаются.
- **Сброс стенда:** MSW в проекте есть, способ сброса выбирается «самым точным и простым» — конкретный механизм зафиксирован в разделе 7 как решение исполнителя.
- **Основные области прогона:** `diff`, `screen`, `sweep`; полный обход сотен экранов — редкий длительный прогон, не ежедневный режим.

## 7. Решения исполнителя (мои; автор может ветировать)

1. **Привязка ответа к виджету и момент сверки.** Соответствие «URL-паттерн → виджет → поля» объявляется в `oracles` профиля; ядро ничего не угадывает. Сверка — только после ожидания привязанного ответа, с явным условием «данные доехали», а не по `domcontentloaded` + макротаску.
2. **`sweep` — не очередь персон.** Находки sweep живут как `finding` со своим режимом повтора и своим курсором; lease/`activeExplorerRuns` (`index.ts:206`) и `routeStages` они не трогают, а `finishRun` (`run-store.ts:597`) проверяет завершённость по фактической области прогона, а не всегда по списку `routes`, иначе sweep-прогон не завершится.
3. **`nonDeterministic` — флаг, а не статус.** Литералы `reproduction.status` не расширяются: от них зависят гейт триажа, `requiresWork()` и гейт экспорта. Экспорт разрешён, но помечается в отчёте и в имени теста.
4. **Механизм сброса.** Базовый — флаг сценария в storage + перезагрузка (не загрязняет маршрут и сигнатуры); уточняющий — служебный эндпоинт сброса моков для случаев, когда перезагрузка ломает сценарий. Query-параметр отклонён: он попал бы в `routeTemplate`, сигнатуры и экспортируемый спек.
5. **Профиль — TS-модуль**, один активный на `stateDir`, выбирается полем `profile` в `config.json`, загружается на прогон; оракулы и контракт исполняются в Node, экстракторы — в странице и возвращают сериализуемый JSON с лимитом и флагом усечения.
6. **Координатные действия под защитой.** `clickAt`/`hoverAt` обязаны разрешиться в семантическую цель (`stage.getIntersection` или элемент под точкой) до `isForbidden`/`isReadOnlySubmission`; при неудаче — отклонение, а не выполнение. Это закрывает обход guard'ов, проверяющих текст только для `click|dblclick|press`.
7. **Тела ответов — не в журнале.** Нормализованный JSON с лимитом и хэшем в шаге, полное тело отдельным артефактом, в кандидате только значения из расхождения.
8. **Сигнатура `dataMismatch` считается отдельно**, чтобы путь поля не схлопывался в `<number>`; подавление применяется на эмиссии и учитывается в precision-метриках; старые глобальные подавления мигрируют в `scope: {}`.
9. **`full` получает чекпоинты** (курсор в `screens.json`), потому что при сотнях экранов прерванный полный обход без курсора означает потерю часов работы.

## 8. Что остаётся открытым или на усмотрение исполнителя

- Финальные имена и схемы новых MCP-инструментов (`bh_crawl`, `bh_extract`, расширенные действия) и итоговое число инструментов.
- Алгоритм ранжирования снимка и конкретный лимит N.
- Способ доступа к Konva stage и three.js scene — по итогам спайка фазы 0.
- Структура `screens.json` и алгоритм шаблонизации маршрутов.
- Значения X и Y в критерии приёмки — после калибровочного прогона.
- Как именно целевой репозиторий добавляет Playwright (devDependency в корне против отдельного воркспейса) — сама необходимость подтверждена автором 2026-11-12, способ размещения выбирает исполнитель (риск R5).

| # | Риск | Последствие | Что делаем |
| --- | --- | --- | --- |
| R1 | Playwright не видит ответы, обслуженные SW (MSW), или не читает их тела | Оракул данных невозможен в заявленном виде | Спайк фазы 0; согласованный запасной путь — хук MSW `response:mock` → `window.__bhResponses`. | R6 | Ядро обрастает BI-спецификой | Потеря расширяемости | Контракт профиля + тест-запрет на упоминания `konva`/`three`/`msw`/`navigator-bi` в `src/**` |
