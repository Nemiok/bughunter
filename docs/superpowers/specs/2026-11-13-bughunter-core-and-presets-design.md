# Bughunter: концепция, core и пресеты — дизайн

Дата: 2026-11-13. Статус: **утверждён автором 2026-11-13** (решения в разделе 7). Прошёл проверку «свежим исполнителем» (builder check): 9 вопросов и 5 фактических расхождений закрыты в разделах 6 и 8.

Предшествующие документы: `2026-11-10-bughunter-mvp-design.md` (MVP, остаётся в силе как описание машины) и `2026-11-12-bughunter-bi-design.md` (BI: профиль, фазы 0–3; фаза 2 этим документом **откладывается** до разреза).

## 1. Контекст и зачем

Bughunter сегодня — один веб-инструмент: MCP-сервер с детерминированной логикой и слой промптов (entry skill, три агента, два скилла-справочника). Что доказано на Qwen Code CLI 1.0.0-preview: полный модельный гейт (5 confirmed, 5 красных e2e-спеков и 5 unit-тестов, 0 подтверждённых ложных, 0 батчинга в оркестрации, run `20261112T072651.852Z-4b2ba4ccfd96`), resume-гейт (4 confirmed, 4 красных спека, run `20261112T114339.688Z-1e5d834da4de`), фаза 1 BI на фикстуре `bi-app` (127 экранов, 0.48 с/экран, 0 провальных находок), BI smoke-прогон с 3 подтверждёнными кандидатами. Автоматический набор — 253 pass + 1 skipped (254).

Автор хочет закрепить **bughunter как концепцию**: набор инструментов и подходов к агентской разработке для поиска багов, где `bughunter-web` — один из пресетов, а другие компетенции (iOS, Android, Node.js) строят своих bughunter'ов по гайдлайнам, **зашитым в сам инструмент**. Модель распространения — как у openspec и Superpowers: один инструмент, метод поставляется файлами, которые читает и человек, и агент.

Проблема в том, что границы сегодня нет физически. В `server/src/` 5188 строк:

| Слой | Модули | Строк | Доля |
| --- | --- | --- | --- |
| Доменно-нейтрально по назначению | `run-store` 673, `tests/verify-red` 301, `tests/detect` 123, `project` 29, `cli-host` 6 | 1132 | 22% |
| Шов (один файл содержит и то и другое) | `index` 508, `reproduce` 337, `types` 225, `detectors/signals` 224, `config` 113, `detectors/index` 2 | 1409 | 27% |
| Веб-адаптер | `browser/*` 1524, `export/playwright` 392, `sweep` 308, `discovery/*` 253, `profile/*` 134, `auth` 36 | 2647 | 51% |

Таблица занижает шов в двух местах, и это важнее самих цифр:

- `tests/verify-red` содержит ~110 строк Playwright-специфики (`Framework = …|'playwright'`, `classifyPlaywrightReport`, `npm exec -- playwright test`, `PLAYWRIGHT_JSON_OUTPUT_FILE`) — модуль **режется**, а не переносится;
- логика `bh_report_candidate` (~120 строк: сигнатура кандидата, дедупликация по `known-bugs.json` и `suppressions.json`, счётчик шагов и `LIMIT_REACHED`, запись кандидата, привязка артефактов) живёт внутри `browser/session.ts` — то есть core-логика sits в 871-строчном веб-модуле.

Контракт типов смешивает домены: `Check.kind` — DOM-слова (`visibleText`, `elementCount`), `StepAction` — глаголы мыши и клавиатуры, `Config` несёт `baseUrl` и `errorBoundarySelector`, `Scope` — литералы `route`/`screen`. Будущее ядро импортирует веб-конфиг: `reproduce.ts:9` и `index.ts:72` тянут `profile/load.ts`.

## 2. Два домена

Вся сущность bughunter лежит в одном из двух доменов. Третьего нет.

**Core — метод и память.** Всё, что верно про поиск багов независимо от вида ПО: жизненный цикл прогона и его состояния; сущности (кандидат, журнал, сигнал, находка, подавление, память известных багов); дисциплина (ничего не заявлено без воспроизведённого симптома, ничего не отдано без red-теста, точность важнее полноты, модель выбирает — код решает); экономика (очередь с lease, дешёвый детерминированный проход, бюджеты, чекпоинты); защитный контур; вердикты тестов; отчёт. В core нет ни одного существительного предметной области: ни браузера, ни DOM, ни HTTP, ни эндпоинта, ни маршрута.

**Preset — органы чувств и руки.** Ответы на пять вопросов, на которые core ответить не может:

1. Что такое **единица исследования**? (web — экран/маршрут; node — эндпоинт)
2. Как **увидеть** цель и что с ней можно **сделать**? (снимок + словарь действий)
3. Что считается **симптомом**? (детекторы)
4. Какое **нарушение инварианта** проверяется детерминированно? (виды `check`)
5. Как **повторить** журнал и какой **тест** из него собрать? (replay + генератор теста)

Плюс схема конфига приложения и тексты агентов.

**Вне обоих доменов:** экземпляр профиля приложения и `config.json` — файлы пользователя, как `.eslintrc`. Core требует наличия слота («новое приложение = новый профиль, пресет не правится»), пресет определяет их форму.

**Правило зависимости:** только `preset → core`, никогда обратно. Пресет является точкой входа MCP-сервера и подключает core как библиотеку; core пресетов не знает и не импортирует.

**Правило установки (решение автора):** **один проект = один пресет.** Core-инструменты у всех пресетов именуются одинаково, поэтому два пресета в одном проекте дали бы коллизию имён MCP-инструментов. Цена принята: full-stack приложение (веб-морда и её же API) одним прогоном не охотится.

**Пограничные случаи** (фиксируются тестами):

| Сущность | Core | Preset |
| --- | --- | --- |
| Экспорт теста | выбор места, защита пути, write-once, запись вердикта | генератор исходника, каталог назначения, `kind` |
| Воспроизведение | протокол «повтор → тот же симптом → удалить шаг», бюджеты, попытки | исполнение шага, вычисление `check` |
| Сигналы | нормализация, алгоритм сигнатуры, дедупликация | источники сигнала |
| Обход (`sweep`) | курсор, чекпоинты, хранилище находок | визит цели: дойти, сбросить, снять, сравнить |
| Кандидат | сборка, сигнатура, дедупликация, лимиты, журнал, артефакты | что считать шагом и симптомом |
| Жизненный цикл сессии | lease-фасад: `EXPLORER_BUSY`, validate/complete/release, откат | open/visit/close конкретной сессии |
| Персоны | механизм lease «цель × персона» | ростер и бриф персоны |
| Вердикты тестов | классификация `red | green | broken`, дедлайны | команда запуска, парсер отчёта, маркер проекта с раннером |
| Отчёт | структура, счётчики, precision-метрики | рендер доменной части находки |
| Промпты | скиллы (контракт, оракулы, правила red-теста, оркестрация) | агенты и скилл словаря пресета |
| Журнал | конверт шага, счётчики, минимизация по конверту | содержимое шага (локатор, координаты, запрос) |

## 3. Цели, не-цели, анти-цели

### Цели

- **C1. Концепция исполняема.** Метод поставляется как скиллы и примеры внутри инструмента: агент, которому сказали «сделай bughunter-ios», читает контракт из установленной поставки.
- **C2. Граница физическая и проверяемая.** Каталоги `core/` и `presets/<name>/`, направление импортов и отсутствие доменной лексики в core закреплены тестами.
- **C3. Второй пресет существует.** `bughunter-node` (HTTP-API) работает и добавлен **нулевым числом правок в core**.
- **C4. Гайдлайны достаточны.** Свежий агент, получивший только скиллы и примеры поставки, собирает работающий игрушечный пресет без разговора с автором.
- **C5. Веб-пресет не теряет доказанного.** Автоматические гейты зелёные, оркестрация не деградирует; исключение — осознанный однократный разрыв схемы состояния (6.10).
- **C6. Один инструмент.** Одно имя, одна установка, одна точка входа на пресет, один проект на пресет.

### Не-цели (этого дизайна)

- Публикация `@bughunter/core` в npm — отложена до появления внешнего автора пресета.
- Фаза 2 BI (оракул данных, `dataMismatch`, областные подавления) — отдельный проект **после** разреза.
- Пресеты iOS/Android — только как читатели гайдлайнов, не как код.
- Несколько пресетов в одном проекте; CI-режим, кластер, параллельные исследователи.
- Манифесты других CLI-хостов (Kimi, Gemini, Muse): поставка остаётся Qwen-совместимой, переносимость не доказывается.
- Визуальная регрессия и пиксельный diff как оракул.
- Миграция старых `state/runs/**` и старых `config.json` на новую схему.

### Анти-цели (что делает результат провалом, даже если код работает)

- **Форк core копированием.** Правило поставки: **пример копируй, core подключай**. Скопированное ядро означает, что каждый производный bughunter заново покупает уже исправленные дефекты (гонка ассерта с ответом сети, `.first()` на скрытом узле, проглоченная ошибка парсинга селектора, недостижимые экраны вне `visited`).
- **Core знает про домен.** Слово `browser`, `dom`, `http`, `playwright`, `konva`, `three`, `msw` в `core/**` — дефект, а не стиль.
- **Пресет требует правки core.** Если `bughunter-node` нельзя добавить без изменения core, граница нарисована неверно; это результат проверки, который надо чинить, а не обходить.
- **Метод понимает только автор.** Гайдлайны без приёмки свежим агентом — документация, а не концепция.
- **Регрессия доказанных гейтов ради красоты структуры.**

## 4. Ограничения

- Node ≥ 22.18, TypeScript со стираемым синтаксисом, запуск без сборки. Зависимости core: `@modelcontextprotocol/sdk`, `zod`. Веб-пресет добавляет `playwright-core`; node-пресет новых рантайм-зависимостей не добавляет (`fetch` встроен), а его фикстура берёт `vitest` как devDependency для экспортируемых тестов.
- Браузер — только установленный Chrome через `channel: 'chrome'` (веб-пресет).
- Промпты на русском, агенты без поля `model`, без дальнейшего делегирования.
- Контракт инструментов жёстко зашит тестами `prompts.bhtest.ts` и `portable.bhtest.ts`: любое переименование требует синхронной правки тестов, промптов и README.
- Пути `.qwen/` чувствительны к записи: CLI отклоняет там Write/Edit, поэтому одноразовые копии для гейтов живут в `bughunter-gate/`, а не в `.qwen/`.
- Ничего не коммитится и не публикуется автоматически.
- Модельные гейты стоят часов (full — 3.5–4 ч, resume — 86 + 13 мин). Пересборка не имеет права требовать их полного повтора там, где достаточно автоматических проверок и одной дешёвой репетиции (6.11).

## 5. Рассмотренные варианты

**A. Манифест без кода.** Концепция — только документы; каждый пресет пишется с нуля.
*Даёт:* нулевая стоимость. *Стоит:* машина не передаётся — ~1130 строк доменно-нейтральной логики и девять исправленных дефектов этого месяца каждый производный bughunter покупает заново. Отклонено.

**B. Публикация `@bughunter/core` + пресеты-пакеты.** *Даёт:* semver-API, обновления через `npm update`. *Стоит:* публикуется догадка о границе (второй реализации нет), плюс версия-матрица, сборка/`exports`, совместимость пакетов. Отклонено как преждевременное; цель фазы D.

**C. Один толстый пакет `@bughunter` с core и presets внутри.** *Стоит:* пресет перестаёт быть снимаемой надстройкой; фикс в `presets/web` поднимает версию core. Отклонено.

**D. Выбрано: один инструмент, монорепо с физической границей, метод как скиллы, второй пресет как учебный пример, публикация отложена.**
*Даёт:* внешнему автору нужно всё сразу — машина, живой пример, гайдлайны; semver-дисциплина не платится заранее; публикация core позже — добавление полей в `package.json`, а не редизайн. *Стоит:* монорепо-инфраструктура (workspaces, общий tsconfig, один `npm test`) и перенос путей, который трогает README, контракт-тесты и `.mcp.json`.

Отклонено отдельно: **пресет как отдельный npm-пакет** (решение автора) — пресеты поставляются каталогами внутри инструмента и выводятся из примеров.

## 6. Архитектура

### 6.1 Инварианты концепции

Семь инвариантов; каждый уже закреплён кодом или тестом и обязан пережить разрез.

1. **Детерминированное — в машине, модель только выбирает.** Лимиты, безопасность, воспроизведение, классификация вердикта модели не делегируются.
2. **Ни одного утверждения без доказательства.** Кандидат подтверждается только после воспроизведения симптома в чистой сессии; баг отдаётся только с red-тестом, вердикт которого получен `bh_verify_red` (`red | green | broken`).
3. **Точность важнее полноты.** Шумный отчёт = провал. Отказ в одно действие, подавления, precision-метрики.
4. **Инструмент не изменяет код приложения и ничего не коммитит.**
5. **Защиты энфорсит код, а не промпт.** Allow-list адресов, запрещённые действия, `readOnly`, разрешение координатного действия в семантическую цель до проверок.
6. **Специфика живёт в пресете и профиле; core доменно-нейтрален.** Закреплено тестом-запретом лексики.
7. **Непроверенное не выдаётся за проверенное.** Статусы, ограничения и пропущенные классы багов публикуются честно; разрез переводит это в требование к отчёту каждого пресета (пропущенные засеянные баги — измеренный базовый уровень, а не умолчание).

Ни один модуль не переносится «как есть»: даже у доменно-нейтральных по назначению есть веб-вкрапления, которые вырезаются в пресет через хуки (6.3).

### 6.3 Контракт пресета

**Пять основных интерфейсов** — прямые ответы на пять вопросов:

| Интерфейс | Ответственность | web сегодня | node |
| --- | --- | --- | --- |
| `TargetInventory` | единицы исследования, шаблонизация, инвентарь | `screens.json` из `bh_crawl` | декларативный список эндпоинтов из профиля |
| `Session` | открыть/закрыть сессию, выполнить действие, снять состояние, писать журнал | Playwright-контекст | HTTP-сессия на `fetch` |
| `Snapshot` | «что здесь можно сделать», ранжирование, лимит | видимые элементы + структура экрана | эндпоинты, последние ответы, новые сигналы |
| `Detectors` | источники сигнала и входы сигнатуры | console, pageerror, requestfailed, HTTP ≥ 400, токены DOM, error boundary | uncaughtException, unhandledRejection, stderr, код выхода, HTTP ≥ 400 |
| `Check` + `Replay` + `TestGenerator` | виды оракулов и их вычисление; исполнение шага журнала; исходник теста | `visibleText`/`notVisibleText`/`elementCount`; переходы и действия; Playwright-спек | `status`/`jsonPath`/`stdout`/`headerContains`; последовательность запросов; Vitest-тест |

**Девять хуков** — то, без чего второй пресет либо правит core, либо копирует его:

| Хук | Зачем |
| --- | --- |
| `TestRunner` | команда запуска, маркер «ближайшего проекта с раннером», парсер отчёта, словарь `kind` |
| `Personas` | ростер и бриф персон |
| `FindingKinds` | словарь видов находок + построитель синтетического шага журнала для `promoteFindingToCandidate` |
| `SweepVisit` | визит цели: дойти, сбросить стенд, снять, сравнить |
| `Reset` | рецепт возврата стенда в известное состояние (web: storage-флаг + reload; node: `POST /__reset`) |
| `ExportTarget` | каталог назначения и `kind` экспортируемого теста |
| `Errors` | реестр доменных кодов ошибок пресета |
| `Compaction` | правило компактизации ответа инструмента (сегодня — стрижка `locator`) |
| `ReportFormat` | рендер доменной части находки и кандидата в отчёте |

`Check` в core — конверт `{ kind: string; target: string; expected?: string | number }`: литералы `kind` объявляет пресет и он же валидирует их при регистрации кандидата. Шаг журнала — то же: core хранит конверт (`id`, `kind`, `timestamp`, `targetRef`, `signalIds`, `responseHashes`) и минимизирует по конверту, содержимое шага принадлежит пресету. `Finding.kind` становится открытым словарём пресета, как `Check.kind`.

### 6.4 Инструменты MCP

19 инструментов сегодняшнего веб-пресета: **11 принадлежит core, 8 пресету**.

| Владелец | Инструменты |
| --- | --- |
| **core** (имена и конверт фиксированы) | `bh_start_run`, `bh_resume_run`, `bh_explore_next`, `bh_finish_run`, `bh_report_candidate`, `bh_reproduce`, `bh_triage`, `bh_promote_finding`, `bh_export_test`, `bh_detect_tests`, `bh_verify_red` |
| **preset** (словарь свой) | web: `bh_open`, `bh_state`, `bh_act`, `bh_navigate`, `bh_probe`, `bh_crawl`, `bh_sweep`, `bh_close`; node: `bh_open`, `bh_state`, `bh_act`, `bh_sweep`, `bh_close` |

Регистрация инструментов происходит в точке входа пресета, но `bh_open`/`bh_close` являются тонкими обёртками над lease-фасадом core: порядок «validate lease → open → record exploring → откат при неудаче» и «close → complete/release» существует в одном экземпляре, потому что именно им доказан resume-гейт.

Переименование `bh_export_e2e → bh_export_test` — единственное намеренное изменение публичного имени: инструмент принадлежит core, а «e2e» — лексика веб-пресета. Стоимость: правка `prompts.bhtest.ts`, `portable.bhtest.ts`, entry skill, текстов агентов, README. Риск изменения поведения модели закрывается route-репетицией (6.11), а не полным гейтом.

### 6.5 Раскладка репозитория

```
bughunter/                      ← один инструмент, одно имя
├── README.md                   ← концепция: инварианты, два домена, как сделать свой пресет
├── core/                       ← машина; отдельно не публикуется
│   ├── src/  ├── test/  └── package.json
├── presets/
│   ├── web/                    ← src/{browser,discovery,export,detectors,profile,sweep,auth}, agents/, skills/, test/
│   └── node/                   ← src/, agents/, skills/, test/ — учебный пример, маленький и читаемый
├── skills/                     ← метод: bughunter (entry), core-contract, preset-guide, oracles, red-test
├── docs/
│   ├── concept/                ← инварианты и гайд автора пресета прозой, шаблоны, examples/
│   └── superpowers/            ← specs, plans, reports (уже есть)
├── fixtures/
│   ├── buggy-app/  bi-app/  jest-app/  vitest-app/
│   └── node-api-app/           ← новая фикстура node-пресета
└── install/                    ← `npx bughunter init --preset web|node`
```

Монорепо на npm workspaces: один lockfile, один `npm ci`, один общий `npm test`, пресеты импортируют core именем пакета (`@bughunter/core` через workspace-симлинк), а не относительным путём. `fixtures/` и `test/` в установленное дерево не едут.

Установленное дерево повторяет раскладку: `.qwen/bughunter/{core,presets/<name>}`, `.qwen/agents/`, `.qwen/skills/`, один `state/` у пресета (`.qwen/bughunter/presets/<name>/state`). `.mcp.json` указывает на точку входа пресета; в репозитории автора — на `presets/web/src/index.ts` напрямую, поэтому монорепо остаётся живой установкой (dogfooding) и не требует отдельной копии.

### 6.6 Промпт-слой

**Скиллы — core, агенты — пресет.** Механизм доказан: агент уже умеет вызывать скилл (`bh-reviewer` вызывает `bughunter-oracles`), поэтому генерация промптов не нужна и общие правила не копируются.

- `skills/bughunter` (entry, **один на инструмент**): стадии, правило «один `Agent` в сообщении», цикл lease, требование red-доказательства, области прогона в нейтральных терминах. Имена инструментов пресета в нём **не** называются.
- `skills/bughunter-core-contract`: инварианты, пять вопросов, четырнадцать интерфейсов, критерий «ноль правок core».
- `skills/bughunter-preset-guide`: как делать свой пресет — от копии примера до приёмки, включая минимальный snippet целевого приложения, чтобы автору не нужны были наши фикстуры.
- `skills/bughunter-oracles`, `skills/bughunter-red-test`: общие правила остаются, доменные примеры уезжают в пресет.
- `presets/<name>/skills/preset-card`: словарь инструментов пресета, его области и `check`-виды.
- `presets/<name>/agents/`: свои `bh-explorer`, `bh-reviewer`, `bh-test-writer`, вызывающие core-скиллы и свой `preset-card`.

Команда запуска остаётся `/bughunter` для всех пресетов: пресет определяется установленной точкой входа и `preset` в `config.json`. Контракт-тесты делятся соответственно: core-часть (строгость оркестрации, allowlist/forbidden, обязательные фразы) живёт в `core/test`, часть пресета (его словарь и allowlist) — в `presets/<name>/test`.

### 6.7 `bughunter-node` — учебный пример

**Цель:** HTTP-API локального сервиса. Не CLI и не библиотека: API задействует максимум понятий core (единица исследования, очередь, персоны, `readOnly`, сигнатура с адресом и статусом, дешёвый обход), оставаясь простым.

**Объём намеренно мал** (это пример, не продукт): ~5 эндпоинтов, 6 засеянных багов, 1 чистый эндпоинт, без автообхода роутеров, без OpenAPI-генерации, без авторизации.

**Фикстура `fixtures/node-api-app`:** сервер на голом `node:http` без рантайм-зависимостей; `vitest` — devDependency фикстуры, туда же кладутся экспортируемые тесты. Реестр засеянных багов живёт в коде (`src/bugs.ts`) с зеркалом `SEEDED.md` — по образцу `bi-app`, чтобы источник правды был один.

| # | Баг | Класс | Как находится |
| --- | --- | --- | --- |
| N1 | необработанное отклонение в обработчике → 500 со стеком наружу | сигнал | детектор |
| N2 | нет валидации: `POST /orders` с отрицательным количеством → 200 и бессмысленный итог | инвариант | `check: jsonPath` |
| N3 | неизвестный id → 200 с `null` вместо 404 | инвариант | `check: status` |
| N4 | неидемпотентная мутация: повторный `POST /payments` списывает дважды | кратность | `check: jsonPath` после двух вызовов |
| N5 | разъезд схемы ответа: поле то `totalCents`, то `total` | данные | **ожидаемый пропуск** (см. ниже) |
| N6 | внутренний текст ошибки (`ECONNREFUSED`, стек) в теле ответа | аномальный токен | детектор |
| — | `/health` всегда корректен | контроль | ложных срабатываний быть не должно |

**N5 — заведомый пропуск.** Мини-оракул схемы ответа — это фаза 2 под другим именем; тянуть его в учебный пресет значит нарушить R4 и отложенную фазу C. N5 остаётся засеянным, чтобы пропуск был **измеренным базовым уровнем**, зафиксированным в отчёте приёмки, а не умолчанием (инвариант 7). Порог ≥ 4 из 6 это учитывает.

**N4 не требует нового механизма.** Нарушение кратности выражается через `check` («после двух POST баланс = X»), а минимизация core уже защищает такие шаги: удаление одного из двух запросов меняет результат `check`, симптом исчезает, шаг сохраняется. Это демонстрация доменной нейтральности протокола воспроизведения, а не новая возможность.

**Персоны:** «интегратор» (ходит по документации), «ревизор» (граничные и невалидные вход, неверные типы), «нетерпеливый» (повторы, параллельные запросы, обрывы). Механизм lease — из core, ростер — пресета.

**Безопасность и сброс:** `allowedHosts` — только локальный стенд; `readOnly: false` в конфиге фикстуры (N2 и N4 требуют POST), вместо него — `forbiddenActionText` на разрушающие пути; reset — `POST /__reset` (аналог `mock-endpoint` в web).

**`sweep` для node:** детерминированный проход по инвентарю с объявленными сценариями (валидный, пустой, невалидный, граничный) без модели, с курсором и чекпоинтами — та же идея, что в web, и лучшее доказательство, что она принадлежит core.

**Экспорт:** Vitest-тест, повторяющий последовательность запросов и утверждающий один симптом; каталог задаётся общим полем `tests.generated.dir`, `kind` — строка пресета (`api`). `bh_detect_tests` и `bh_verify_red` используются через хук `TestRunner` без правок core.

**Приёмка — двумя слоями.**

*Детерминированный (без модели, минуты):* `test/node-api-acceptance.bhtest.ts` под флагом, по образцу `bi-app-acceptance.bhtest.ts`, — sweep по 5 эндпоинтам × 4 сценария, промоция находок, воспроизведение, экспорт Vitest-теста, вердикт `red` от `verify-red`.

*Модельный (часы):* прогон в одноразовой копии, 3 персоны × 5 эндпоинтов = 15 задач в очереди.

**Критерий приёмки:**
1. `bughunter-node` добавлен **нулевым числом правок в `core/`** — проверяется diff'ом и тестом на направление импортов.
2. Модельный прогон находит **≥ 4 из 6** засеянных багов и **0** подтверждённых ложных срабатываний; пропуски (N5 как минимум) публикуются измеренным базовым уровнем.
3. Каждый подтверждённый баг имеет Vitest-тест с вердиктом **`red`**, полученным независимым запуском, а не со слов модели.
4. Автоматический набор зелёный (253+ pass, 0 fail; skipped остаётся под флагом), `typecheck` зелёный, веб-пресет проходит route-репетицию (6.11).
5. Приёмка гайдлайнов (6.8) пройдена.

### 6.8 Приёмка гайдлайнов

Гайдлайны проверяются, а не декларируются.

- **Харнесс:** отдельный headless-процесс `qwen -p` в одноразовой копии в `bughunter-gate/guidelines-check/` (вне `.qwen/`, потому что CLI отклоняет запись в чувствительные пути). Поставка читается из копии, результат пишется туда же.
- **Задание:** собрать игрушечный пресет для нового вида цели — «CLI-утилита: запуск с аргументами, проверка stdout и кода выхода». Мини-фикстуру агент берёт из snippet'а в `preset-guide`, а не из наших `fixtures/`, иначе доказательство перестаёт быть независимым.
- **Доказательство работы:** stdio-рукопожатие скриптом (по образцу `portable.bhtest.ts`) плюс один модельный прогон на мини-фикстуре в копии, где `.mcp.json` настроен с самого начала. Действий пользователя не требуется: сервер называется `bughunter` и уже разрешён по имени в user settings.
- **Артефакт:** отчёт в `docs/superpowers/reports/` и сохранённый игрушечный пресет в `docs/concept/examples/` как второй учебный пример (в `presets/` он не попадает — это не поддерживаемый пресет).
- **Цикл при провале:** до двух итераций, каждая со свежим агентом и свежей копией. Провал — это дефект гайдлайнов (конкретное место, где пришлось угадывать), а не дефект агента.
- **Самодостаточность:** приёмка читает только скиллы и примеры поставки; `docs/concept/` поставляется, но не требуется. Значит контракт и гайд обязаны быть полными внутри `SKILL.md`.

### 6.9 Конфиг и профиль

Общие поля `config.json` (владеет core): `preset`, `profile`, `limits.stepsPerSession`, `limits.candidatesPerRun`, `safety.forbiddenActionText`, `safety.readOnly`, `tests.unit.command`, `tests.generated.dir`, `baseBranch` и карта целей для области `diff`.

Поля пресета: web — `baseUrl`, `allowedOrigins`, `routes`, `browser`, `detectors`, `limits.elementsPerSnapshot`, `limits.screensPerSweep`, `limits.responseSettleMs`; node — `baseUrl`, `allowedHosts`, `scenarios`, `reset`.

Инвентарь целей не дублируется: `routes`/`screens.json` у web и список эндпоинтов у node живут там, где им место — инвентарь приложения в **профиле** (он про приложение), ограничение области прогона в **config** (он про установку). `ProfileSchema` — это zod-схема TS-модуля профиля и его загрузчик; оба принадлежат пресету, core требует только наличия слота.

### 6.10 Совместимость состояния и конфига

Решение автора: **однократный разрыв, без миграции.** Мы до публикации, единственный пользователь — автор, а доказательства гейтов уже зафиксированы в отчётах и README (run id, счётчики, пути JSONL), поэтому старым `state/runs/**` не нужно оставаться читаемыми.

Нейтральная лексика в схеме состояния: `routeStages → targetStages`, литералы области `route|screen → target`, `tests.e2e.dir → tests.generated.dir`, `kind` записи теста — строка пресета (`e2e` для web, `api` для node), `Check.kind` и `Finding.kind` — открытые словари пресета, `Step.routeTemplate → Step.targetRef`. Шаблон конфига перегенерируется (`CONFIG_CREATED`), конфиги фикстур и живой `config.json` автора правятся тем же коммитом; compat-шеймов не пишем.

### 6.11 Route-репетиция (определение)

Единственное модельное доказательство, разрешённое после разреза.

- **Фикстура и область:** `buggy-app`, `route /orders/new` (та же область, что в resume-гейте).
- **Харнесс:** headless `qwen -p` в одноразовой копии в `bughunter-gate/`, точечный allow-list в `.qwen/settings.json` копии, без `--dangerously-skip-permissions`.
- **PASS:** CLI exit 0; run `finished`; **0 батчей** (не более одного tool_use на assistant-сообщение); ≥ 1 confirmed; красный спек на подтверждённого кандидата, вердикт которого перепроверен **моим** запуском `npx playwright test`, а не отчётом модели.
- **Бюджет:** ≤ 1 ч. Действий пользователя не требуется.
- **Для node-пресета:** одна репетиция области поверх детерминированной приёмки 6.7.

### 6.12 Дистрибуция

- Одно имя: `bughunter` в npm свободно (проверено 2026-11-13); скоуп `@bughunter` резервируется, `@bughunter/core` **не публикуется** до фазы D.
- Установка: `npx bughunter init --preset web|node` раскладывает `.qwen/bughunter/{core,presets/<name>}`, `.qwen/agents/`, `.qwen/skills/` и добавляет блок в `.mcp.json`; при установке пакетом `.mcp.json` указывает в `node_modules/…`, при портативной — в скопированное дерево. Пересинхронизация — `bughunter update`.
- Правило для сторонних пресетов: **пример копируй, core подключай** (workspace/git-зависимость сейчас, npm позже).
- Канал плагина/маркетплейса (как у Superpowers) рассматривается в фазе D как альтернатива `init`; в этом дизайне не реализуется.

## 7. Решения, принятые автором

- **2026-11-13.** bughunter закрепляется как **концепция** (набор инструментов и подходов к агентской разработке для поиска багов); `bughunter-web` — пресет/надстройка; другие компетенции строят своих bughunter'ов в той же идеологии.
- **2026-11-13.** Ровно **два домена**: **core** (термин автора, вместо «kernel») и **preset**. Все сущности лежат в одном из них; цель — когнитивная простота и возможность делать open source пресеты поверх core.
- **2026-11-13.** Пресет **не** поставляется отдельным пакетом: один инструмент `bughunter`, внутри него гайдлайны, скиллы и примеры, из которых пресет выводится (модель openspec/Superpowers).
- **2026-11-13.** Второй пресет — **`bughunter-node`**, простой, потому что разрабатывается легче остальных.
- **2026-11-13.** Цель node-пресета — **HTTP-API**; порядок работ — **разрез → node → оракул данных**.
- **2026-11-13.** **Один пресет на проект**: full-stack приложение одним прогоном не охотится, коллизии имён MCP-инструментов не возникает.
- **2026-11-13.** Разрез выполняется **до** фазы 2 BI, хотя после builder check известно, что это полноценный рефакторинг шва, а не перенос файлов.
- **2026-11-13.** Совместимость `state/*.json` и `config.json` **ломается однократно**, миграция не пишется.

## 8. Решения исполнителя (мои; автор может ветировать)

1. **Пресет — точка входа MCP-сервера, core — библиотека.** Альтернатива «core регистрирует инструменты пресета» возвращает доменную логику в core.
2. **Lease-фасад живёт в core**, `bh_open`/`bh_close` пресета — тонкие обёртки: порядок вызовов, которым доказан resume-гейт, не дублируется в каждом пресете.
3. **Четырнадцать интерфейсов вместо восьми.** Builder check показал, что восьми не хватает: `verify-red` содержит Playwright, `run-store` — персоны и веб-отчёт, `sweep` — браузерный reset, `bh_report_candidate` — внутри `browser/session.ts`. Без новых хуков node-пресет либо правит core, либо его копирует.
4. **`/bughunter` остаётся одной командой** на все пресеты; словарь инструментов пресет сообщает через свой `preset-card`-скилл, который агент вызывает (механизм доказан на `bughunter-oracles`). Генерация промптов не вводится.
5. **Фикстура `node-api-app` на голом `node:http`**; `vitest` — devDependency фикстуры, а не рантайма сервера.
6. **Инвентарь эндпоинтов декларативный** (профиль), автообход роутеров не делается: он фреймворко-специфичен и учебному примеру не нужен.
7. **Переименование `bh_export_e2e → bh_export_test`**; риск изменения поведения модели закрывается route-репетицией.
8. **Модельные гейты после разреза не повторяются полностью:** достаточно автоматического набора, `portable`-рукопожатия и route-репетиции (6.11) на каждом пресете. Основание: семантика промптов не меняется, кроме одного имени инструмента.
9. **N5 объявлен ожидаемым пропуском** node-пресета: мини-оракул схемы — это фаза 2 под другим именем.
10. **N4 ловится существующей минимизацией**: `check` на кратность делает оба запроса необходимыми шагами.
11. **`readOnly: false` + `forbiddenActionText`** в конфиге node-фикстуры, reset — `POST /__reset`.
12. **Приёмка гайдлайнов — headless-копия вне `.qwen/`**, snippet фикстуры в гайде, доказательство — stdio-рукопожатие плюс один модельный прогон; артефакт сохраняется в `docs/concept/examples/`; до двух итераций со свежим агентом.
13. **Монорепо на npm workspaces**, пресет импортирует core именем пакета; в репозитории автора `.mcp.json` указывает на `presets/web/src/index.ts`, поэтому монорепо остаётся живой установкой.
14. **Инвентарь приложения — в профиле, область прогона — в config**; `ProfileSchema` = zod-схема профиля и загрузчик, оба в пресете.
15. **Skipped-тест замера стоимости обхода bi-app остаётся под флагом** и не входит в критерии фаз A и B (минуты против часов).
16. **Инвариантов семь, а не шесть:** честность заявлений выделена отдельно, потому что разрез делает её требованием к отчёту каждого пресета.

## 9. Что остаётся открытым или на усмотрение исполнителя

- Точные имена модулей, типов и экспортов core-API; форма конверта шага журнала.
- Как `install/` решает, ставить из `node_modules` или копировать дерево (до первого внешнего пользователя достаточно копирования); нужен ли `bughunter update` в первой поставке.
- Пороги X/Y для `node-api-app` — после калибровочного прогона, заранее не выдумываются.
- Судьба `.qwen/settings.json.example` и корневого `.mcp.json` в новой раскладке.
- Точный список запрещённых слов в тесте-запрете лексики (входят ли `route`, `screen`, `endpoint`, `spec` в именах полей состояния после 6.10).

## 10. Порядок работ

| Фаза | Что | Критерий |
| --- | --- | --- |
| **R** | Закрыть текущую готовность: оценка BI smoke-прогона, отчёт, README, ревью ветки, интерактивный trust | README честен, все гейты записаны |
| **A** | Разрез `core/` + `presets/web/` (рефакторинг шва по 6.2–6.3, переименования по 6.10), скиллы концепции, тесты границы | автоматический набор зелёный, `typecheck` зелёный, route-репетиция PASS, тесты на направление импортов и лексику проходят |
| **B** | `presets/node` + `fixtures/node-api-app` + приёмка 6.7 и 6.8 | ≥ 4/6 багов, 0 ложных, red-тесты перепроверены, **ноль правок core**, игрушечный пресет собран свежим агентом |
| **C** | Фаза 2 BI: оракул данных, `dataMismatch`, областные подавления — в новой раскладке | приёмка BI-дизайна §5.4 (пороги X/Y) |
| **D** | Дистрибуция: `init`/`update`, публикация `@bughunter/core`, канал плагина | внешний автор ставит и запускает без участия автора |

Основание порядка A → B → C: фаза 2 ложится ровно на модули шва (`detectors/signals`, `reproduce`, `export`, `types`, `run-store` — находки и подавления). Писать её в смешанном дереве значит резать дважды: и ядро, и свежий оракул.
