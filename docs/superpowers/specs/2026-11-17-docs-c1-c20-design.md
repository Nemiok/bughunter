Дата: 2026-11-17.

## Контекст

Handoff `docs/superpowers/handoff/2026-11-17-v0.1.0-handoff.md` оставляет после релиза `v0.1.0`
проход по 20 противоречиям и пробелам авторской документации из
`docs/concept/examples/cli-preset/PRESET-NOTES.md`. Выбранная форма работы — точечная
синхронизация актуальных документов с текущим кодом и CLI-шаблоном, плюс недостающие тесты
шаблона. Runtime-поведение core, web и node не меняется.

Перед дизайном заново проверены исходное состояние и гейты:

- web — 258 pass + 1 skipped, typecheck трёх workspace-пакетов чист;
- plugin build — 14 components, 30.6 MB; install check — web 19 tools/7 skills/6 agents,
  node 16 tools, dormant 0 tools без создания state;

  marketplace — чистый репозиторий на `8cb30c9`.

Эти измерения — baseline, а не доказательство будущих правок. После реализации гейты повторяются.

## Цель и критерий завершения

Активные руководства и промпт-слой не должны содержать противоречий C1–C20, перечисленных в
историческом отчёте. Для каждого пункта выполняется одно из двух:

1. исправляется актуальный канонический документ или тест шаблона;
2. фиксируется, что актуальный документ уже корректен либо замечание относится только к
   историческому отчёту и не требует переписывания provenance.

Завершение требует зелёной автоматической линии, явной сверки всех C1–C20 и чистого git-diff,
не содержащего изменений runtime-кода core/web/node.

`plugin/dist/` не редактируется вручную. `plugin/build.mjs` копирует канонические скиллы и шаблон,

остаются снимками конкретной приёмки. В них не переписываются наблюдения, окружение или результаты.

## Решения по C1–C20

### C1. Учебный пример для нового домена

Гайд больше не направляет автора нового домена копировать только `presets/web`. Основной образец —
`docs/concept/examples/cli-preset/preset`; web и node называются поддерживаемыми образцами для
соответствующих доменов. Plugin-вариант использует `<installPath>/template/cli-preset` через
существующий build preamble и `AUTHORING.md`.

### C2. Пять вопросов и девять хуков

Текст явно говорит, что перечисление после пяти вопросов не добавляет независимый второй набор.
Девять имён — финальный чек-лист хуков: уже назначенный `TestRunner` и восемь ещё не назначенных,
включая `ProfileSchema`. Это не девять новых интерфейсов в дополнение к пяти вопросам.

### C3. Шестнадцать интерфейсов и восемнадцать полей

Контракт различает 16 доменных интерфейсов и 18 обязательных полей `Preset`: дополнительные поля —
`name` и `configSchema`. `assertPreset` проверяет все 18. Формулировки в гайде, prose-guide и
plugin authoring приводятся к этому же различению.

### C4. Владелец протокола воспроизведения

Актуальный contract-скилл уже правильно относит цикл, бюджеты и минимизацию к
`core/src/reproduce.ts`, а пресету оставляет `Replay`, вычисление check и артефакты. Противоречивые
формулировки не возвращаются; существующий boundary-тест должен остаться зелёным.

### C5. Имена тестовых файлов

Гайд называет фактическую раскладку шаблона:

- `test/acceptance.bhtest.ts` — детерминированная приёмка;
- `test/preset.bhtest.ts` — поля `Preset` и stdio-handshake/portable-контракт;
- `test/prompts.bhtest.ts` — агенты и карта;
- `test/import-boundary.bhtest.ts` — новый тест направления импортов.

Функциональное требование важнее выдуманного имени `<name>-acceptance`/`portable`; существующие
файлы не переименовываются ради формального совпадения.

### C6. Тест направления импортов

В CLI-шаблон добавляется `test/import-boundary.bhtest.ts`. Он рекурсивно читает собственный
`src/` и отклоняет импорты чужих пресетов: относительные пути в `presets/` и пакеты
`@bughunter/<other>`; `@bughunter/core` разрешён. Проверка содержит отрицательные примеры, чтобы
ошибочный matcher не прошёл незамеченным.

Границу «core не импортирует пресеты» по-прежнему проверяет core-сьют. Standalone-шаблон не должен
знать расположение внешнего core и потому не дублирует это сканирование.

### C7. Inventory builder необязателен

Entry-скилл требует вызова inventory-builder только если карта пресета объявляет такой инструмент.
Для статического инвентаря CLI/node лишний вызов не выдумывается: `bh_start_run` использует
`TargetInventory`. Для web карта по-прежнему называет `bh_crawl`.

### C8. Владелец reset-рецепта

Доменно-нейтральный entry не приписывает reset всегда профилю. Он отправляет к карте пресета:
web использует рецепт из профиля, node и CLI — рецепт из `config.json`. Текст
`RESET_UNSUPPORTED` описывает отсутствие рецепта у пресета, а не универсально у профиля.

### C9. Оракулы вне DOM

`bughunter-oracles` начинается с доменно-нейтральных правил: ожидание/факт, наблюдаемый симптом,
сигнал важнее выдуманного check, обязательная форма check из карты. DOM/API/CLI приводятся как
примеры сигналов и оракулов. Для CLI явно названы exit code, stdout, stderr и кратность эффекта.
Metadata `whenToUse` не ограничивает применение только страницей; соответствующее ожидание
существующего prompt-теста обновляется.

### C10. Red-тесты вне Jest/Vitest

`bughunter-red-test` содержит общие правила и отдельные framework-specific указания для Jest,
Vitest и `node:test`. Для `node:test` названы `node:assert/strict`, изоляция временных данных,
`spawnSync`/запуск процесса по контракту пресета и очистка в `finally`. Описание скилла не
обещает поддержку только Jest/Vitest.

### C11. `check` при промоции находки

Документируются одновременно два факта, без изменения схемы:

- MCP transport-schema оставляет `check` optional;
- рабочий протокол требует передавать валидный check всегда: без него кандидат не получает
  проверяемого оракула и не должен отправляться в обычный reproduce/export-поток.

Опциональность транспортного поля не представляется как разрешение пропускать оракул.

### C12. Ответ `bh_close` и артефакты

Карты/гайд не обещают артефакты в ответе close. `bh_close` закрывает сессию, завершает lease или
освобождает его и возвращает `{ ok: true }`; путей к артефактам в этом конверте нет. Артефакты повтора возвращает
replay/reproduce. Журнал и пути состояния определяются картой и сохранённым run/state layout.

### C13. `limits.candidatesPerRun`

Гайд прямо называет поле валидируемым, но неэнфорсимым. Оно не перечисляется как работающая защита
или гарантированный лимит.

### C14. `LIMIT_REACHED`

Контракт прямо назначает лимит шагов сессии пресету. В шаблоне это проверка в выполнении действия;
отдельного core-хука нет.

### C15. Недостижимый баг фикстуры

Требование переформулируется: хотя бы один засеянный баг остаётся недостижимым для
детерминированного sweep при объявленных сценариях/reset, а не для модели в домене вообще. Модель
может найти его; пропуск sweep публикуется с измеренным baseline. Пример C3 корректен именно как
пробел детерминированного покрытия.

### C16. Незапущенные гейты в отчёте строителя

Это историческое ограничение конкретного запуска, а не текущая инструкция. Отчёт не правится.
Текущий baseline и послерелизная линия проверяются командами handoff; существующая route-репетиция
остаётся отдельным модельным доказательством и не выдаётся за свежий запуск.

### C17. Версия Node в отчёте строителя

Историческое расхождение окружения не переписывается. Актуальные install/authoring docs сохраняют
поддерживаемое требование Node `>=22.18` и не приписывают текущей среде версию из старого отчёта.

### C18. Пути `.mcp.json` и standalone-копия

Гайд различает репозиторную раскладку `.qwen/bughunter/...` и standalone-шаблон, где точка входа —
`preset/src/index.ts` скопированного дерева. Plugin-автор следует `AUTHORING.md` и не создаёт
репозиторные `presets/<name>`/`.mcp.json` по инструкции для исходника Bughunter.

### C19. Имя сгенерированного теста

Контракт оставляет имя `ExportTarget.fileName`; гайд называет это обязанностью пресета. Для
CLI-шаблона зафиксировано `${bugId}.test.ts`. Требование TypeScript сохраняется, а red должен быть
падением assertion, не загрузки файла.

### C20. `bh_detect_tests` и `tests.unit.command`

Гайд разделяет обнаружение и исполнение. `bh_detect_tests` сообщает configured unit command.
`TestRunner.command` получает `unitCommand`, но пресет сам решает, применимо ли оно к однофайловому
вердикту. CLI-шаблон возвращает configured command из detect, а фактический verify использует
собственный `node:test` TAP-wrapper; это не скрывается под общим обещанием запуска любой команды.

`README.md` обновляется до фактических 68 core, 58 node (52 pass + 6 skipped), 259 web

## Проверка

После правок выполняются:

1. CLI-шаблон: `node --test --test-concurrency=1 test/*.bhtest.ts` и typecheck; новый
   import-boundary тест включён в общий набор.
2. Core: `npm test && npm run typecheck` — ожидаемый baseline 68/68 сохраняется, если тесты не
   потребуют обновления ожиданий; фактический итог фиксируется по выводу.
3. Node: `npm test && npm run typecheck`; затем acceptance с `BH_NODE_ACCEPTANCE=1` и возврат
   `fixtures/node-api-app/ACCEPTANCE.md` к исходной версии.
4. Web: `npm test && npm run typecheck`.
5. Monorepo: `npm run typecheck --workspaces` из `.qwen/bughunter`.
6. Plugin: `node plugin/build.mjs && node plugin/test-install.mjs`; проверяются 14 components,
   web 19/7/6, node 16 и dormant 0/state=false.
7. Финальная сверка C1–C20 с дизайном, `git diff --check`, `git status` и просмотр итогового diff.

Если существующий docs/prompt-тест требует старую формулировку, сначала проверяется, что ожидание
действительно относится к исправленному противоречию; меняется только это ожидание. Ослаблять
проверку или удалять тест нельзя.

Модельные прогоны не запускаются: для них требуется отдельное разрешение. Документационный diff не
получает новое модельное доказательство и не претендует на него.

## Release и git-границы

`plugin/release/bughunter-0.1.0.zip`, SHA-файл и marketplace `8cb30c9` не обновляются: они
принадлежат тегу `v0.1.0` на `19f144f`. Сборка после правок обновляет только ignored
`plugin/dist/` и доказывает работоспособность рабочего дерева. Распространение новых docs/template
изменений требует отдельного release-решения, а не подмены артефактов `v0.1.0`.

Push и публикация не выполняются. Единственный разрешённый на этапе дизайна commit содержит только
этот spec. Коммиты реализации, если они понадобятся, требуют отдельного разрешения.
