# PRESET-NOTES — журнал угадывания и дефектов документации

Пресет: `@bughunter/cli`, каталог `toolkit/presets/cli/`.
Цель: CLI-утилита (`cli-app/`), запуск процесса с argv, чтение stdout/stderr и кода выхода.
Работа велась только по файлам копии; внешние источники не использовались. `toolkit/core/`,
`toolkit/presets/web/`, `toolkit/presets/node/`, `.qwen/`, `docs/concept/` и `.mcp.json` не правились.

Обозначения:

- **D (decision)** — гайд или контракт не ответил на вопрос, решение принято самостоятельно.
- **C (contradiction/gap)** — документация противоречит коду, другому скиллу или самой себе;
  либо требуемый гайдом артефакт не создан.
- **E (edit)** — место, где пришлось бы править поставляемый код, если бы это было разрешено.
- **O (observation)** — измеренное поведение поставленного кода, важное для понимания решения.

Ссылки на строки даны по состоянию копии на момент сборки.

## 1. Решения, которых не было в гайде (D)

### D1. Домен и единица исследования
Гайд описывает только web- и node-примеры. Для CLI пришлось определить: цель — **шаблон
команды** (`add <name> <qty>`, `show <name>`, `list`), а конкретный запуск — шаг журнала.
Конкретный argv в `target` отвергается как `TARGET_NOT_ALLOWED`; слова передаются в `argv`
инструмента `bh_act`. Это зафиксировано в карте пресета и в описаниях инструментов.

### D2. Форма действия
`SessionHandle.act(payload: unknown)` в core не задаёт форму payload. Выбран `CliActInput`:
`argv: string[]` без имени исполняемого файла и необязательный `setup: string[][]`. Процесс
запускается без оболочки (`shell: false`), поэтому аргумент с пробелом или кавычкой остаётся
одним словом. `setup` выполняется в той же базе и попадает в журнал одной записью вместе с
основной командой.

### D3. Источник инвентаря
`TargetInventory.templateOf` синхронный и не получает `stateDir`, поэтому профиль нельзя
прочитать из него. Решение: `cliInventory.list` читает профиль приложения, а `templateOf`
пользуется статическим словарём известных шаблонов (`add`, `show`, `list`). Это ограничение
домена: при добавлении команды в профиль нужно обновить и словарь в `src/inventory.ts`.

### D4. Соответствие scope
Core `Scope = 'diff' | 'full' | 'target' | 'sweep'` (`toolkit/core/src/types.ts:2`). Для одной
цели используется `target`; отдельного `explore` в core нет. Для `diff` взят `targetMap` из
конфига (`cli-app/src/**` → три шаблона), для `full` — весь инвентарь профиля.

### D5. Где живёт состояние
По умолчанию `stateDir` — `toolkit/presets/cli/state/` рядом с точкой входа
(`src/paths.ts`). `BUGHUNTER_STATE_DIR` переопределяет каталог. Иначе сервер, запущенный из
корня копии, `toolkit/` или установленного `.qwen/bughunter/`, писал бы состояние в разные места.
В копии проверен только вариант запуска из корня копии по `.mcp.json`.

### D6. Первый запуск и `CONFIG_CREATED`
`ensureConfig` в core возвращает `config` только если файл уже был, а `createdPath` — только
после создания. `bh_start_run` создаёт шаблон и в этом же вызове возвращает `CONFIG_CREATED`,
то есть первый вызов завершается ошибкой, а повторный уже работает. Это выбрано, чтобы создание
конфига не выглядело как успешно начатый прогон. Гайд описывает только сам факт `CONFIG_CREATED`.

### D7. Рецепт сброса
Рецепт объявлен в конфиге (`reset: { kind: 'delete-db' }`), а не в профиле. При отсутствии
рецепта `cliReset.apply` бросает `RESET_UNSUPPORTED`; core ловит это в `runSweep` и один раз на
прогон пишет находку `reset-unsupported`. Сессия модели при отсутствии рецепта получает
доменную ошибку, а не молчаливое продолжение на грязной базе.

### D8. Виды check
Выбраны шесть видов: `exitCode`, `stdoutContains`, `stdoutNotContains`, `stderrContains`,
`stderrNotContains`, `stdoutOccurrences`. Для кратности нужен `pointer` — подстрока, число
вхождений которой проверяется. Core `Check` не содержит `pointer`
(`toolkit/core/src/types.ts:96`), поэтому в пресете объявлен `CliCheck = Check & { pointer?: string }`.

### D9. Оракул судит последний запуск
`SessionHandle` не даёт языка запросов по журналу. Проверка `check` смотрит только последний
запуск сессии. Чтобы проверить несколько команд, нужно несколько кандидатов или `setup` в
последнем шаге. Это записано в карте и в описании `bh_report_candidate`.

### D10. Детекторы
Детекторы CLI: `exit-code` (таймаут, ошибка spawn, сигнал, код вне `allowedExitCodes`),
`stderr-stack` (маркеры стека в stderr или stdout), `anomaly` (токены из
`detectors.anomalyTexts`). `allowedExitCodes` для фикстуры — `[0, 2]`: неизвестная команда
объявлена контрактом как код 2, и это не баг.

### D11. Симптомы, журнал и артефакты
Шаг журнала — плоский `CliStep` (`StepBase & { argv, setup, exitCode, signal, durationMs }`).
Полный журнал запусков дополнительно пишется в `executions.jsonl`. `bh_close` сохраняет журнал,
но не прикрепляет артефакты к кандидату; артефакты появляются после воспроизведения. Это
поведение core, отдельного решения пресета здесь нет.

### D12. Воспроизведение
`cliReplay` открывает чистую сессию, применяет reset, повторяет шаги с их `argv` и `setup`,
собирает сигналы и артефакты. Совпадение — либо сигнатура совпала, либо `check` нарушен.
Неполный шаг (нет `argv`) даёт `matched: false` и `REPLAY_STEP_INCOMPLETE`. `abort` закрывает
только сессию этого экземпляра replay, поэтому параллельные кандидаты не мешают друг другу.

### D13. Тестовый раннер
В Node v24 нет встроенного JSON-репортёра `node:test`, а core `verifyRed` читает JSON. Решение:
собственный TAP-парсер `src/test-report.ts`, который запускает `node --test` и переводит TAP в
нейтральный JSON. Из окружения дочернего процесса удаляется `NODE_TEST_CONTEXT`, иначе
вложенный `node --test` пропускает выбранный файл. Виды теста — `cli` и `node-test`.

### D14. Куда и как экспортируется тест
Каталог — `tests.generated.dir` из конфига (`test/bughunter`), имя — `<bugId>.test.ts`, вид —
`cli`. Файл генерируется как TypeScript с `node:test`, `spawnSync` и временной базой через
`mkdtempSync(join(tmpdir(), 'bh-cli-'))`. Тест утверждает **требуемое** поведение, а не
наблюдаемое: для C1 — `assert.equal(last.exitCode, 2)`, а не фактическую единицу.

### D15. `exportTest` и текущий каталог
Core `exportTest` ищет проект от `process.cwd()` вверх до `.git`
(`toolkit/core/src/project.ts:17`, `toolkit/core/src/export-host.ts:55`). Пресет временно делает
`process.chdir(appDir)` вокруг вызова core и восстанавливает каталог в `finally`. Это
process-global обход; при одновременном экспорте из двух сессий возможна гонка (см. E4).

### D16. `verifyRed` и временный каталог
Core `verifyRed` создаёт временный каталог в OS `tmpdir()`
(`toolkit/core/src/verify-red.ts:135`), то есть вне копии. В тестах `TMPDIR` переопределяется
на каталог внутри `presets/cli`, чтобы не выходить за границу копии. В реальном запуске тест
использует системный tmp — это поведение core, не пресета.

### D17. Персоны
Ростер: `бухгалтер`, `ревизор`, `нетерпеливый`. Брифы:
`бухгалтер` идёт по объявленным сценариям; `ревизор` проверяет границы, невалидный ввод,
пропущенные и лишние аргументы; `нетерпеливый` повторяет команды, смешивает подготовку и
чтение, использует пробелы и специальные символы. Гайд требует ростер и бриф, но не задаёт
конкретные CLI-персоны.

### D18. Агенты и их allowlist
Созданы три агента с точными списками инструментов:
- `bh-explorer`: `bh_open`, `bh_state`, `bh_act`, `bh_report_candidate`, `bh_close`, `Skill`;
- `bh-reviewer`: `Read`, `Grep`, `Glob`, `bh_triage`, `Skill`;
- `bh-test-writer`: `Read`, `Grep`, `Glob`, `Edit`, `Write`, `bh_detect_tests`, `bh_export_test`,
  `bh_verify_red`, `Skill`.

Главному агенту карта разрешает `bh_sweep`; инструменты сессии ему запрещены. Словарь отказов:
`FAILED: <код>`, `RETRY_LATER: EXPLORER_BUSY`, `Кандидатов нет`. Эти формулировки выбраны,
гайд задаёт только требование самоодостаточного финального сообщения.

### D19. Карта пресета
Карта называет ровно пять инструментов взаимодействия, области, инвентарь, сценарии, reset и
шесть видов `check`. Она не содержит инструмента построения инвентаря: инвентарь статичен и
читается профилем. Это расходится с формулировкой entry-скилла (см. C7).

### D20. Обход: сценарии, сброс и принадлежность цели
`bh_sweep` выполняет **все** объявленные сценарии, относящиеся к текущей цели, а не один.
Перед каждым сценарием база сбрасывается. Принадлежность сценария цели вычисляется по первой
команде argv через профиль; если команда не найдена — `SCENARIO_INVALID`. Находки обхода не
являются кандидатами; для разбора нужна промоция с обязательным `check`.

### D21. Находки и кандидаты
После промоции находка получает синтетический журнал из одной команды сценария
(`src/finding-kinds.ts`). Дальше работают обычные `bh_reproduce`, `bh_triage`, `bh_export_test`.
Без `check` кандидата нечем воспроизвести; генератор теста в этом случае бросает
`TEST_GENERATION_UNSUPPORTED`.

### D22. Доменные коды
Коды пресета перечислены в `src/errors.ts`: `CHECK_INVALID`, `COMMAND_NOT_FOUND`,
`EXECUTION_FAILED`, `EXECUTION_TIMEOUT`, `FORBIDDEN_ACTION`, `PROFILE_INVALID`,
`PROFILE_NOT_FOUND`, `RESET_FAILED`, `RESET_UNSUPPORTED`, `SCENARIO_INVALID`,
`SESSION_NOT_FOUND`, `TARGET_NOT_ALLOWED`, `TARGET_REQUIRED`, `TEST_DATA_PATH_UNSAFE`.
`INVENTORY_EMPTY` и `TARGETS_EMPTY` переводятся в `COMMAND_NOT_FOUND`.

### D23. Защита
`readOnly` запрещает команды с `mutates: true` до spawn. `forbiddenActionText` проверяется по
строкам argv и setup. Путь к entry и к базе проверяется `safeJoin` (`APP_ENTRY_UNSAFE`,
`DATABASE_PATH_UNSAFE`). Эти коды сейчас не входят в `cliDomainCodes`, поэтому при аварии
могут попасть в модель как `TOOL_FAILED` (см. E5).

### D24. Фикстура
Взят snippet из шага 6 гайда без изменения логики: `cli-app/src/cli.js`. Добавлены
`package.json` с маркером `bughunter.target: "cli"`, `SEEDED.md` и `.gitignore`. C1–C4 и
контрольный `list` сохранены. C3 оставлен для модели: sweep его не покрывает, потому что
сброс перед каждым сценарием изолирует два `add` друг от друга.

### D25. Тесты пресета
Одиннадцать файлов `test/*.bhtest.ts`: конфиг, сессия, checks/detectors, replay, sweep,
export/verify, reporter, контракт пресета и handshake, промпты, детерминированная приёмка.
Счётчик в приёмке намеренно не фиксирует точное число находок: `findings >= 7`, потому что
детали сценариев могут добавлять находки, не меняя вердикт.

### D26. Модельный слой
Модельный прогон на фикстуре в этой работе не выполнялся: по заданию его запускает харнесс в
свежей сессии после сдачи. Детерминированная приёмка (sweep → promote C1 → reproduce 2/2 →
triage confirmed → export → red) выполнена тестом. C3, C2 и C4 проверены базовой линией
фикстуры, но не подтверждены моделью в этой сессии.

## 2. Противоречия и пробелы документации (C)

### C1. Нет CLI-примера, хотя гайд велит копировать `presets/web`
`bughunter-preset-guide`, шаг 1: `cp -R presets/web presets/<name>`. В поставке есть только
`presets/web` и `presets/node`; CLI-домена нет. Пришлось собирать раскладку по контракту и
обоим примерам. Это не ошибка реализации, а пробел гайда: для нового домена нет учебного
примера, кроме двух соседних.

### C2. «Пять вопросов» и «девять хуков» пересекаются
`bughunter-preset-guide`, шаг 3: сначала пять вопросов, затем «девять хуков: `TestRunner`,
`Personas`, …». `TestRunner` уже входит в ответ на пятый вопрос («как повторить и какой тест
собрать»). В итоге непонятно, девять хуков — это девять **новых** слотов или девять **всего**,
включая уже названные. Пришлось считать по `Preset`/`assertPreset`, а не по тексту.

### C3. «Шестнадцать интерфейсов» против восемнадцати полей `Preset`
`bughunter-core-contract` называет 16 интерфейсов, но `Preset` требует 18 полей: к 16 строкам
таблицы добавляются `configSchema` и `name` (плюс `configSchema` упомянут отдельным абзацем).
`assertPreset` проверяет именно поля, поэтому ориентиром служил код, а не число в заголовке.

### C4. Где живёт протокол воспроизведения — противоречие внутри контракта
`bughunter-core-contract`, таблица границы: в колонке core написано «протокол повтора, бюджеты
и минимизация — в `core/src/reproduce.ts`», затем в той же строке — «Сейчас протокол и бюджеты
живут в пресете», а в колонке пресета — «а сегодня также протокол повтора и его бюджеты».
Ниже, в разделе «Что объявлено, но ещё не перенесено», сказано обратное: цикл живёт в
`core/src/reproduce.ts`, пресет реализует только `Replay`. Фактически (`O`) core владеет
циклом и бюджетами; пресет реализует `replay`, `check` и артефакты. Пришлось верить коду.

### C5. Имена тестовых файлов из шага 7 не совпадают с созданными
Шаг 7 требует `test/<name>-acceptance.bhtest.ts` и `test/portable.bhtest.ts`. Созданы
`test/acceptance.bhtest.ts` (детерминированная приёмка) и `test/preset.bhtest.ts` (контракт
`Preset` + stdio-handshake). Функционально требования покрыты, но имена другие. Это
осознанное отклонение, чтобы не раздувать число файлов; при строгой приёмке по именам его
нужно устранить переименованием.

### C6. Тест направления импортов не создан
Шаг 7 требует отдельный тест, запрещающий `from '.*presets/` и `@bughunter/<other>` внутри
`core/` и внутри своего пресета. Такого файла в пресете нет. Запрет соблюдается вручную:
`toolkit/presets/cli/src` импортирует только `@bughunter/core`, `node:*`, `zod` и свои
относительные модули; `core/` не менялся. Автоматической проверки этого правила в наборе
пресета нет — это незакрытое требование гайда.

### C7. Entry-скилл требует «инструмент построения инвентаря», которого нет в карте
`.qwen/skills/bughunter/SKILL.md:13`: «Для обхода всего инвентаря сначала вызови инструмент
построения инвентаря, затем `bh_start_run`…». Карта CLI-пресета такого инструмента не
объявляет: инвентарь статичен и читается из профиля, а `bh_start_run` сам вызывает
`cliInventory.list`. Либо entry-скилл предполагает другой пресет, либо карта обязана объявлять
builder. Пришлось выбрать статический профиль и не регистрировать лишний инструмент.

### C8. «Профиль» против «конфига» в описании `RESET_UNSUPPORTED`
`.qwen/skills/bughunter/SKILL.md:15` говорит: «профиль приложения не задаёт рецепт сброса
данных». В контракте и карте рецепт сброса живёт в `config.json` (`reset`), а профиль отвечает
за инвентарь. Наблюдаемая находка `reset-unsupported` приходит из конфига. Формулировка
скилла вводит в заблуждение о владельце рецепта.

### C9. `bughunter-oracles` написан про страницу и DOM
Скилл говорит о странице, error boundary, селекторах и координатах. Для CLI пришлось
переводить его правила в «ожидаемый exit code / stdout / stderr», «сигнал важнее check»,
«оракул обязателен», «не принимать ожидаемые 401/404 и ошибки третьей стороны за баг».
Прямого CLI-раздела в скилле нет; это дефект применимости, а не логики.

### C10. `bughunter-red-test` знает только Jest и Vitest
Скилл требует `jest.fn`/`vi.fn`, fake timers и моки. CLI-пресет генерирует `node:test`-тесты
(в поставке нет Jest/Vitest), поэтому правила пришлось перенести на `node:assert/strict`,
`spawnSync`, изоляцию через временную БД и очистку в `finally`. Скилл не описывает `node:test`,
хотя node-пример поставки тоже может его использовать.

### C11. `bh_promote_finding`: описание требует `check`, схема — нет
Описание инструмента: «Обязателен check — иначе кандидата нечем воспроизвести». Zod-схема
делает `check` необязательным (`z.strictObject({ …, check })`, где `check` сам `.optional()`).
Это унаследовано от core-контракта. Пресет валидирует `check`, если он передан, но не может
сделать его обязательным без расхождения с ядром; без `check` кандидат дойдёт до генератора и
получит `TEST_GENERATION_UNSUPPORTED`.

### C12. `bh_close` не возвращает артефакты
Entry-скилл и карта говорят, что `bh_close` сохраняет журнал, но модели обещаны артефакты
сессии. Фактически `lifecycle.close` возвращает `{ ok: true }`, а артефакты появляются только
при воспроизведении. Модель не получает ссылку на `executions.jsonl` из ответа `bh_close`;
путь приходится знать из карты/соглашения. Это расхождение между ожиданием «артефакты после
сессии» и фактическим конвертом.

### C13. `limits.candidatesPerRun` не энфорсится
Контракт сам предупреждает об этом, но гайд шага 5 перечисляет `limits` как общий механизм.
В пресете лимит только валидируется схемой; фактического ограничения числа кандидатов нет.
Полагаться на него нельзя.

### C14. `LIMIT_REACHED` — обязанность пресета, а не core
Контракт относит лимит шагов к пресету; в `Preset` нет отдельного хука для него. Пришлось
встроить проверку в `performCommand`. Это не противоречие, а неочевидное место: без чтения
раздела «Что объявлено, но ещё не перенесено» легко решить, что лимит уже в core.

### C15. Гайд обещает «заведомо недостижимый» баг, а C3 достижим моделью
Шаг 6: «Один баг оставь заведомо недостижимым для своего домена». В CLI C3 (повторный `add`)
достижим моделью; недостижим он только для детерминированного sweep из-за сброса перед каждым
сценарием. Мы оставили C3 непокрытым sweep и опубликовали это в `SEEDED.md`, но формально это
не «заведомо недостижимый для домена» баг. Требование гайда и выбранная фикстура расходятся.

### C16. Модельный прогон и полная линия монорепо не выполнены
Шаг 8 требует: модельный прогон (≥3 из 4 багов, 0 ложных), весь набор монорепо зелёный,
`typecheck` зелёный, web-пресет проходит route-репетицию. В этой работе выполнены только
CLI-тесты и `typecheck` CLI; модельный прогон отложен харнессу, полная линия монорепо и web
route-репетиция не запускались. Это честно отмечено в `BUILD-REPORT.md`, а не выдано за успех.

### C17. Окружение заявляет Node v26.3.0, фактически v24.14.0
В описании окружения указано `Node.js version: v26.3.0`; `node -v` в копии дал `v24.14.0`.
Пресет проверяет только `>= 22.18`, поэтому работает, но отчёт о среде и реальность расходятся.
Возможные различия в поведении `node:test` и TAP между версиями не проверялись.

### C18. `.mcp.json` в гайде и в копии описывают разные раскладки
Шаг 2 гайда задаёт `.qwen/bughunter/presets/<name>/src/index.ts`, а в копии `.mcp.json`
указывает `toolkit/presets/cli/src/index.ts` (так требует харнесс). Оба пути ведут к одной
точке входа, но документация не объясняет, что в копии `toolkit/` играет роль
`.qwen/bughunter/`. Пришлось считать относительные пути гайда путями внутри `toolkit/`.

### C19. Шаг 7 говорит «сгенерированный тест — TypeScript», но не задаёт имя файла
Контракт `ExportTarget` оставляет имя файла пресету. Выбрано `<bugId>.test.ts`; это решение,
а не требование гайда. Расширение `.ts` проверено: `node --test` в v24 запускает файл, а
`node:test` видит тесты.

### C20. `bh_detect_tests` и `tests.unit.command`
Контракт перечисляет `tests.unit.command` как общее поле, но не говорит, обязан ли раннер
использовать его как команду запуска. В пресете поле используется только для ответа
`bh_detect_tests`; фактический запуск всегда идёт через собственный TAP-репортёр. Это
осознанное решение, но гайд не описывает такое расщепление.

## 3. Где пришлось бы править поставляемый код (E)

Правки не вносились. Перечислены места, где обходной путь в пресете хуже прямой поддержки core.

### E1. `Check` без `pointer`
`Check = { kind, target, expected? }` (`toolkit/core/src/types.ts:96`). Для
`stdoutOccurrences` нужна искомая подстрока. Пришлось объявить `CliCheck` и собственную
`cliCheckSignature`, потому что core-сигнатура не учитывает `pointer`. Если бы `pointer` был
частью конверта, сигнатура и дедупликация работали бы одинаково у всех пресетов.

### E2. `SessionHandle` и `StepBase` слишком нейтральны
`SessionHandle.act(payload: unknown)` возвращает `unknown`, а `StepBase` не содержит
доменных полей. Пресет сужает типы через `Omit` и касты (`CliSessionHandle`, `CliStep`).
Это работает, но касты в replay/report — цена отсутствия generic-параметров у core-типов.

### E3. `verifyRed` жёстко использует OS `tmpdir()`
`mkdtemp(join(tmpdir(), 'bh-verify-red-'))` (`toolkit/core/src/verify-red.ts:135`) выходит за
пределы проекта. В тестах это обходится переопределением `TMPDIR`; в реальной установке
временные файлы всё равно окажутся в системе. Если бы core принимал базовый каталог или
использовал каталог проекта, поведение было бы предсказуемее и не требовало бы подмены env.

### E4. `exportTest` зависит от `process.cwd()` и `.git`
`findProjectRoot()` (`toolkit/core/src/project.ts:17`) и `nearestOwnedProject`
(`toolkit/core/src/export-host.ts:55`) ищут проект от текущего каталога. Пресет делает
`process.chdir(appDir)` на время экспорта. Это глобальная мутация процесса: при двух
одновременных экспортах возможна гонка, а при сервере, запущенном из неожиданного каталога,
поведение зависит от окружения. Прямое решение — передавать `projectRoot` в `exportTest`.

### E5. Реестр доменных кодов неполон
`errorCode` (`src/errors.ts`) отдаёт `TOOL_FAILED` для кодов, которых нет в `cliDomainCodes`:
`APP_ENTRY_UNSAFE`, `DATABASE_PATH_UNSAFE`, `REPLAY_STEP_INCOMPLETE`,
`TEST_ASSOCIATION_INCOMPLETE`, `TEST_GENERATION_UNSUPPORTED`. Эти коды бросает сам пресет, но
они не попадают в модель как доменные. Частично это можно исправить в пресете (добавить коды в
список), частично — только расширением контракта `Errors`, если считать их общими для домена.

### E6. `TargetInventory.templateOf` без контекста
`templateOf(value: string): TargetRef` (`toolkit/core/src/preset.ts:12`) синхронный и не получает
`stateDir`. Поэтому инвентарь нельзя прочитать из профиля в этом методе, и приходится держать
статический словарь шаблонов. Если бы core передавал контекст (или делал метод асинхронным),
профиль оставался бы единственным источником правды.

### E7. `candidatesPerRun` нигде не энфорсится
Контракт признаёт это, но ограничение заявлено в `limits`. Прямое исправление — проверка в
core при `reportCandidate`. Пресет не может надёжно ограничить число кандидатов, потому что
не владеет их созданием.

### E8. Артефакты не прикрепляются к кандидату при `bh_close`
Кандидат создаётся с `artifacts: []`, а `attachCandidateArtifacts` — отдельный проход. Если
модель закроет сессию и не передаст артефакты, в кандидате останется только журнал. Прямое
исправление — в core при закрытии сессии или при `reportCandidate` прикреплять артефакты
сессии. Пресет не может сделать это за core без дублирования его хранилища.

### E9. `errors` не даёт способа объявить новые коды без правки core
`Errors.codes` — это карта переводов, а список допустимых кодов определяется в пресете
вручную (`cliDomainCodes`). Если бы контракт позволял объявлять словарь кодов как данные,
`errorCode` не пришлось бы расширять при каждом новом доменном исключении.

### E10. `findProjectRoot` не принимает стартовый каталог в `exportTest`
`exportTest` вызывает `findProjectRoot()` без аргумента. В тестах и при сервере это означает
зависимость от cwd. Прямое исправление — параметр `projectRoot` в `ExportInput`, как это уже
сделано в других местах core.

## 4. Наблюдения о поставленном коде (O)

- `O1`. Core `ensureConfig` возвращает `config` только при существующем файле; при создании —
  только `createdPath`. Это не баг, но влияет на D6.
- `O2`. `readFindings` экспортируется из core и используется в приёмке; это удобно, но
  контракт не упоминает его в списке инструментов/интерфейсов.
- `O3`. `runSweep` сам пишет находку `reset-unsupported` и сам вызывает `options.reset.apply`;
  пресетный `cliSweepSession` намеренно запрещает `act`, поэтому обход не может случайно
  выполнить действие модели.
- `O4`. `NODE_TEST_CONTEXT` наследуется дочерним `node --test` и приводит к пропуску файла;
  без удаления переменной reporter возвращает «0 tests» и `verifyRed` классифицирует это как
  `broken`. Это воспроизведено и исправлено в `src/test-report.ts`.
- `O5`. На macOS `realpath` меняет `/var` на `/private/var`; без него отчёт и аргумент
  `verifyRed` указывают на разные пути. Исправлено в `verifyCliRed`.
- `O6`. `node --test` в v24 не поддерживает встроенный JSON-репортёр, поэтому TAP-парсер —
  вынужденная мера, а не украшение.
- `O7`. Сгенерированный тест запускается из каталога приложения; `DB_FILE` указывает на
  временную базу, созданную в `mkdtempSync(tmpdir())`. Это не трогает `orders.json` фикстуры.
- `O8`. `state/config.json` содержит `tests.unit.command: "node --test"` — то же, что шаблон
  `cliConfigTemplate()`. Ранее в файле стоял `null`; расхождение устранено.
- `O9`. `reset-unsupported` объявлен в словаре находок и действительно создаётся core, но
  `cliSweepVisit` не создаёт его сам: он ловит отказ `cliReset.apply` и оставляет находку core.
- `O10`. `bh_sweep` в карте разрешён главному агенту; `bh_open`/`bh_state`/`bh_act`/`bh_close`
  — только `bh-explorer`. Это соответствует entry-скиллу, но требует, чтобы harness установил
  агентов именно с такими allowlist.

## 5. Итог по документации

Самые дорогие пробелы для автора нового пресета:

1. Нет CLI-примера и нет раздела «как перевести оракулы страницы в оракулы процесса» (C1, C9).
2. Противоречие о владельце протокола воспроизведения (C4) и неполный список доменных кодов
   (E5) заставляют читать core вместо контракта.
3. Entry-скилл предполагает инструмент построения инвентаря, которого нет в карте (C7).
4. Шаг 7 требует тест направления импортов, но в поставке нет ни примера, ни шаблона (C6).
5. `bh_promote_finding` и `bh_close` описаны сильнее, чем их фактические конверты (C11, C12).

Все перечисленные места либо обойдены в пресете, либо честно оставлены незакрытыми и
перечислены в `BUILD-REPORT.md`.
