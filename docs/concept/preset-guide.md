# Как сделать свой пресет Bughunter

Прозаическая версия скилла `bughunter-preset-guide`: тот же маршрут, но с объяснением, почему шаги
именно такие. Модель внутри прогона читает скилл `bughunter-preset-guide`; этот документ — для
человека. Контракт, состав интерфейсов и таблица границы — в [`invariants.md`](invariants.md)
и в скилле `bughunter-core-contract`.

**Пример копируй, core подключай.** Основной учебный пример нового домена — `docs/concept/examples/cli-preset/preset`; `presets/web` и `presets/node` — поддерживаемые образцы для браузерного и HTTP-доменов, а не библиотеки для наследования. Для нового домена скопируйте CLI-шаблон и замените его домен, а core подключите именем пакета `@bughunter/core`; web/node используйте как дополнительные доменные образцы, а не как альтернативу этой команде. `presets/web` — точка отсчёта для всего, что исследуется через браузер: единица исследования — экран, действие — клик или ввод, регрессионный тест — Playwright. `presets/node` — точка отсчёта для HTTP-домена: единица исследования — эндпоинт, действие — один запрос, оракулы `status`/`jsonPath`/`headerContains`, регрессионный тест — Vitest. Наследование от чужого пресета запрещено так же, как правки core. Критерий готовности — **ноль правок core**.

## Что нужно сделать

Пресет отвечает на пять вопросов (см. `invariants.md`) и реализует 16 интерфейсов и два служебных поля — всего 18 полей Preset из
`core/src/preset.ts`. Практический порядок такой.

### 1. Скопировать пример и завести пакет

```bash
cp -R docs/concept/examples/cli-preset/preset .qwen/bughunter/presets/<name>
rm -rf .qwen/bughunter/presets/<name>/state
```

Команда запускается из корня репозитория Bughunter. В standalone-копии `cli-preset` точка входа — `preset/src/index.ts`, а фикстура — `cli-app/`; plugin-автор следует `AUTHORING.md` и не переносит репозиторный `.mcp.json` без пересчёта пути.

В `.qwen/bughunter/presets/<name>/package.json` — имя `@bughunter/<name>`, `"type": "module"`, `engines.node >= 22.18`, зависимость `"@bughunter/core": "*"`, скрипты `test` (`node --test --test-concurrency=1 test/*.bhtest.ts`), `typecheck`, `start` (`node src/index.ts`). Свои рантайм-зависимости объявляйте здесь: core их не тянет. Затем добавьте `"presets/<name>"` в `workspaces` файла `.qwen/bughunter/package.json` и выполните `npm install` из `.qwen/bughunter` — core придёт workspace-симлинком, lockfile на всё дерево один.

Сборка не нужна: Node ≥ 22.18 исполняет `.ts` снятием типов. `tsconfig.json` оставьте как в примере,
он нужен только для `tsc --noEmit`.

### 2. Ответить на пять вопросов интерфейсами

Каждый ответ ложится в конкретный интерфейс; порядок ниже — порядок, в котором удобно реализовывать.

- **Единица исследования** → `TargetInventory`: список целей и приведение конкретного значения
  к шаблону. У web это `state/screens.json`, построенный обходом ссылок; у node будет декларативный
  список эндпоинтов из профиля.
- **Как увидеть и что сделать** → `Session` (открыть сессию цели от имени персоны), `SessionHandle`
  (снять состояние, выполнить действие, отдать шаги и артефакты, закрыться), `Snapshot` (что из
  снимка отдавать модели: ранжирование, лимит, отсечение лишнего), `Detectors` (источники симптома).
- **Какое нарушение проверяется** → `Checks`: словарь видов `check`, валидация формы и вычисление
  нарушения на сессии.
- **Как повторить и какой тест собрать** → `Replay` (исполнение журнала в чистой сессии),
  `TestGenerator` (исходник теста из кандидата), `TestRunner` (команда запуска, парсер отчёта
  в нейтральную `TestRunSummary`, признак ближайшего проекта с раннером).

Финальный чек-лист из девяти хуков: `TestRunner`, `Personas`, `FindingKinds`, `SweepVisit`, `Reset`, `ExportTarget`,
`Errors`, `ReportFormat`, `ProfileSchema`. `TestRunner` уже назначен пятым вопросом, остальные восемь добавляются теперь; это не девять лишних интерфейсов. Всё вместе собирается в объект `Preset` из 18 полей, включая `name` и `configSchema`:

```ts
import { assertPreset, type Preset } from '@bughunter/core/preset.ts';

export const myPreset = assertPreset({
  name: 'my-domain',
  configSchema: myConfigSchema,      // commonConfigSchema.extend({ … })
  inventory: myInventory,
  session: mySession,
  snapshot: mySnapshot,
  detectors: myDetectors,
  checks: myChecks,
  replay: myReplay,
  generateTest: myTestGenerator,
  profile: myProfileSchema,
  testRunner: myTestRunner,
  personas: myPersonas,
  findingKinds: myFindingKinds,
  sweepVisit: mySweepVisit,
  reset: myReset,
  exportTarget: myExportTarget,
  errors: myErrors,
  report: myReportFormat,
}) satisfies Preset;
```

`assertPreset` проверяет состав при старте сервера: недостающее поле даёт `PRESET_INVALID: <поле>`
сразу, а не в середине четырёхчасового прогона. Пока интерфейс не реализован, держите в слоте
заглушку, бросающую доменный код ошибки: сервер стартует, а непроверенная возможность не выдаёт
себя за работающую — инвариант 7. Заглушка — приём разработки, а не поставляемое состояние:
в поставляемых пресетах их нет, и `core/test/contract-usage.bhtest.ts` не пропускает
`pending(`/`PRESET_HOOK_NOT_WIRED` в файлах сборки.

### 3. Зарегистрировать инструменты

`src/index.ts` — точка входа MCP-сервера. Одиннадцать имён core фиксированы и одинаковы у всех
пресетов; инструменты взаимодействия — ваш словарь (у web их восемь). Схемы аргументов пишите
`z.strictObject`: лишнее поле модели должно отклоняться сразу, а не игнорироваться молча.

`bh_open` и `bh_close` не изобретайте: это тонкие обёртки над lease-фасадом core (`createLifecycle`).
Порядок «validate lease → open → record exploring → откат при неудаче» и «close → complete/release»
существует в одном экземпляре, и именно им доказан resume-гейт. Доменные коды ошибок переводите на
границе через `Errors.codes`, чтобы модель видела лексику своего домена, а не нейтральные коды core.

### 4. Конфиг и профиль

Схема конфига — `commonConfigSchema.extend({ … })`. Общие поля (`baseBranch`, `profile`,
`targetMap`, `limits`, `safety`, `testDataPrefix`, `tests.unit.command`, `tests.generated.dir`)
принадлежат core; свои (`baseUrl` и `allowedOrigins` у web, `baseUrl` и `allowedHosts` у node)
объявляете вы.

`limits.candidatesPerRun` валидируется, но не энфорсится. `LIMIT_REACHED` проверяет сессия пресета при действии. `tests.unit.command` сообщается через detect и передаётся раннеру, но однофайловый verify может использовать собственный reporter/wrapper; CLI-шаблон именно так запускает `node:test` через TAP-wrapper.

Шаблон создаётся при первом запуске (`CONFIG_CREATED`), несоответствие схеме
отклоняется с именем поля (`CONFIG_INVALID: <файл>: <проблема>`).

Инвентарь приложения не дублируйте в конфиг: ограничение области прогона живёт в `config.json`
(он про установку), инвентарь — в профиле приложения (он про приложение). Профиль загружает
`ProfileSchema`; новое приложение — новый профиль, пресет при этом не правится.

### 5. Взять минимальное целевое приложение

Для приёмки не нужны фикстуры bughunter: минимальное целевое приложение со засеянными багами и
чистой командой для контроля лежит в скилле `bughunter-preset-guide` (шаг 6) — это CLI-утилита
учёта заказов с четырьмя засеянными багами. Реестр багов держите в коде с зеркалом в `SEEDED.md`:
приёмка считает покрытые и пропущенные, и пропуск обязан быть измеренным базовым уровнем в отчёте,
а не умолчанием. Оставьте хотя бы один баг недостижимым для детерминированного sweep при заданных
сценариях/reset, но не требуйте недостижимости для модели. Опубликуйте измеренный baseline этого пропуска.

### 6. Написать тесты пресета

- `test/acceptance.bhtest.ts` — детерминированная приёмка без модели: обход, промоция, воспроизведение, экспорт и red-вердикт; медленную приёмку держите под флагом.
- `test/preset.bhtest.ts` — поля `Preset`, словари и stdio-handshake: `initialize` → `tools/list`, состав инструментов и изоляция state.
- `test/prompts.bhtest.ts` — allowlists агентов, карта пресета и обязательные фразы.
- `test/import-boundary.bhtest.ts` — запрет импортов чужих пресетов в собственном `src`; `@bughunter/core` разрешён, а границу core проверяет core-сьют.

`ExportTarget.fileName(bugId)` принадлежит пресету; CLI-шаблон использует `${bugId}.test.ts`. Red-тест обязан падать на assertion симптома, а не на загрузке TypeScript-файла.

Прогон — `npm test --workspaces --if-present` из корня монорепо. Зелёная линия web-пресета: 0 fail
и один пропущенный тест под флагом замера стоимости; core — все тесты зелёные. Точные счётчики
здесь намеренно не приведены: они устаревают в том же коммите, где их написали. Свои тесты
добавляйте к этой линии, не ослабляя чужие.

### 7. Пройти приёмку

Приёмка проводится в одноразовой копии **вне** `.qwen/` (CLI относит такие пути к чувствительным и
отклоняет запись субагента), с настроенным `.mcp.json` и без действий пользователя: сервер
называется `bughunter` и уже разрешён по имени в user settings.

1. **Ноль правок core** — diff ветки пуст по `core/`, тесты направления импортов и запрета доменной
   лексики зелёные.
2. **Детерминированный слой** — приёмка из шага 6 проходит без модели, за минуты.
3. **Модельный слой** — один прогон в копии: не меньше 3 из 4 засеянных багов и **0** подтверждённых
   ложных срабатываний; пропуски опубликованы измеренным базовым уровнем.
4. **Red-доказательство** — на каждый подтверждённый баг есть тест с вердиктом `red`, полученным
   независимым запуском, а не со слов модели.
5. **Автоматическая линия** — весь набор монорепо зелёный, `typecheck` зелёный, web-пресет проходит
   route-репетицию.
6. **Гайдлайны проверены, а не декларированы** — отдельный headless-агент собирает игрушечный пресет
   для нового вида цели, читая только скиллы и примеры поставки. Провал трактуется как дефект
   гайдлайнов (конкретное место, где пришлось угадывать), а не как дефект агента; до двух итераций,
   каждая со свежим агентом и свежей копией.

Артефакт приёмки — отчёт в `docs/superpowers/reports/` и сохранённый игрушечный пресет в
`docs/concept/examples/` как второй учебный пример: в `presets/` он не попадает, потому что не
поддерживается.

## Чего делать не нужно

- Править core под свой домен. Нужен новый механизм — сначала расширьте интерфейс в core отдельной
  задачей с собственным тестом.
- Наследоваться от другого пресета или копипастить его модули целиком: общий код живёт в core.
- Держать инвентарь целей в двух местах (в конфиге и в профиле) — разъедется на первом же прогоне.
- Ослаблять `z.strictObject` до `z.object`, чтобы «модель не спотыкалась»: лишнее поле, принятое
  молча, — это непроверенное поведение, то есть нарушение инварианта 7.
- Писать в промпте запрет, который должен энфорсить код (инвариант 5).
